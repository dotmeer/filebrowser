# Инструкции для агента

Self-hosted веб-файлменеджер для доверенной сети. Стек: .NET 10,
ASP.NET Core, Blazor Interactive Server, Minimal API, Microsoft.Data.Sqlite,
YamlDotNet, xUnit, OpenTelemetry.

## Перед работой

1. Прочитай `docs/SPEC.md` и `docs/PROJECT_STATE.md`.
2. Проверь `git status`, изучи относящийся к задаче код и тесты.
3. Для эксплуатационных задач прочитай `docs/OPERATIONS.md`.

SPEC задаёт требования; код и тесты показывают фактическую реализацию;
PROJECT_STATE содержит текущие ограничения и результаты проверок.
Не считай документацию доказательством работоспособности. Противоречия,
влияющие на данные, безопасность или публичный контракт, не разрешай молча.

## Область работы

- Выполняй только порученную задачу, не добавляй функции из roadmap.
- Не создавай репозиторий, commit или push без явного поручения.
- Не запускай подагентов без поручения пользователя.
- Сохраняй пользовательские изменения; не используй destructive Git-команды.
- Не переписывай проект целиком ради смены архитектуры.
- Не создавай дополнительные roadmap/status-файлы. Задание на конкретную
  работу допустимо по поручению пользователя; общее состояние остаётся
  в PROJECT_STATE, направления развития — только в ROADMAP.

## Архитектура и безопасность

- Один серверный и один тестовый проект; без EF Core, CQRS, mediator,
  микросервисов и отдельного SignalR Hub.
- Интерфейсы нужны на реальных границах, не для каждого класса.
- Blazor и HTTP используют общие прикладные сервисы. Серверный компонент
  не вызывает HTTP API собственного приложения.
- Содержимое файлов, включая текст предпросмотра, не передаётся через
  Blazor circuit; для него используется обычный HTTP.
- Клиент передаёт root + относительный path. Все файловые операции проходят
  общий resolver/validator: границы по сегментам, проверка всех компонентов,
  отказ при symlink и специальных файлах.
- Не раскрывай физические пути в DTO/HTTP-ошибках и не логируй содержимое файлов.
- Корни нельзя удалять, переименовывать или перемещать. Недоступный корень
  не останавливает запуск и перепроверяется при следующем обращении.
- Изменяющие HTTP-запросы требуют antiforgery; permissive CORS запрещён.
- Не заявляй защиту от враждебного локального процесса без механизма и тестов.

## Данные и операции

- Соблюдай SPEC: конфликт имени — ошибка, без перезаписи и автосуффиксов.
  `Exists` не заменяет атомарную защиту от конкурентной публикации.
- Copy/move/delete: источники из одной папки, ordinal-порядок, полная
  предпроверка с накоплением ошибок; исполнение до первой ошибки, без отката
  уже выполненных объектов. Move удаляет источник только после публикации;
  fallback copy+delete допустим только при подтверждённой cross-device ошибке.
- Удаление — только фоновой задачей через зарегистрированный временный
  артефакт. Не удаляй объекты по одному лишь совпадению префикса.
- Upload: один файл — один raw POST с Content-Length и antiforgery;
  временный файл зарегистрирован, публикация без перезаписи, cleanup при
  неуспехе, лимит `uploads.maxFileBytes`; upload не занимает очередь worker.
- ZIP: поток без временного файла, NoCompression, предпроверка до ответа,
  ошибка после начала ответа обрывает соединение; лимиты из SPEC §12.2.
- Не выполняй полный обход дерева синхронно в UI-контексте компонента.
- SQLite: параметризованные запросы, нумерованные миграции, короткие
  транзакции; без транзакции на время файлового ввода-вывода и без совместного
  использования одного соединения конкурентными операциями.
- SQLite — источник истины для задач. При reconnect состояние перечитывается.
  Очистка истории не изменяет файлы и не теряет регистрацию оставшихся артефактов.
- Недоступная/повреждённая SQLite останавливает запуск; автовосстановления нет.

## Проверки и документация

- Изменение поведения сопровождай регрессионным тестом. Для System.IO и
  SQLite используй временные каталоги/БД, для HTTP — WebApplicationFactory;
  не заменяй реальные файловые сценарии одними моками.
- Базовые проверки: `dotnet build`, `dotnet test`, `docker build -t filemanager .`,
  `docker compose config`. Запускай применимые к изменению проверки.
- Linux-специфичные сценарии проверяй в Linux. Недоступная среда означает
  «не запускалось», а не «пройдено».
- Не устраняй падение теста удалением проверки или ослаблением безопасности.
  Если тест закрепляет дефект, объясни исправление ожидаемого поведения.
- Документация и ответы — на русском, имена кода/API — на английском.
- При изменении контракта/конфигурации обновляй SPEC и README; при изменении
  схемы добавляй миграцию; новую зависимость обосновывай.
- OTLP опционален, настройки — стандартные `OTEL_*`; инструкция в OPERATIONS.
- По окончании обнови PROJECT_STATE: фактическое состояние, открытые проблемы,
  точные проверки, ограничения среды и следующий шаг. Не накапливай историю
  сессий, закрытых дефектов и заменённых решений.
- В ответе кратко сообщи результат, проверки, ограничения и следующий шаг.
