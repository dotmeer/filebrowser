# Инструкции для агента

## Назначение проекта

Self-hosted веб-файлменеджер для доверенной сети.

Стек:
- .NET 10 LTS;
- ASP.NET Core;
- Blazor Interactive Server;
- Minimal API;
- Microsoft.Data.Sqlite;
- YamlDotNet;
- xUnit;
- OpenTelemetry.

## Обязательное чтение

В начале каждой сессии:

1. Прочитай `docs/SPEC.md`.
2. Прочитай `docs/PROJECT_STATE.md`.
3. Проверь `git status`.
4. Изучи относящийся к текущей итерации код.
5. Для эксплуатационных задач также прочитай `docs/OPERATIONS.md`.

Не делай вывод о состоянии проекта только по документации.
Сверяй её с кодом и доступными проверками.

## Источники истины

- SPEC — требования.
- PROJECT_STATE — текущее состояние и передача между сессиями.
- Код и тесты — фактическая реализация.

При противоречии не выбирай молча удобную версию.
Опиши расхождение и запроси решение, если оно влияет на данные,
безопасность или публичный контракт.

## Режим работы

- Выполняй только запрошенную итерацию.
- Не переходи автоматически к следующей.
- Не добавляй функции из roadmap.
- Не создавай Git-репозиторий: его создаёт пользователь.
- Не создавай commit и не выполняй push без явного поручения.
- Не запускай подагентов без поручения пользователя.
- Не перезаписывай пользовательские изменения.
- Не используй destructive Git-команды.
- Не переписывай проект целиком ради смены архитектуры.
- Не создавай альтернативный план вместо обновления существующего состояния.

Если итерация слишком велика, раздели её на подэтапы
в PROJECT_STATE и честно зафиксируй незавершённость.

## Архитектура

- Один серверный проект и один тестовый проект.
- Без EF Core, микросервисов, CQRS и mediator-фреймворков.
- Интерфейсы нужны на реальных границах, не для каждого класса.
- Общие правила файловых операций находятся в прикладных сервисах.
- Minimal API и Blazor используют одни и те же сервисы.
- Серверные Blazor-компоненты не вызывают HTTP API собственного приложения.
- Не создавай отдельный SignalR Hub в MVP.
- Файловые байты никогда не передаются через Blazor circuit.
- Upload и ZIP не входят в MVP — не реализуй их и не закладывайся на них.

## Безопасность

- Клиент передаёт root + относительный path.
- Не раскрывай физические пути в DTO и API-ошибках.
- Любая файловая операция проходит общий resolver/validator.
- Проверяй границу корня по сегментам.
- Проверяй все существующие компоненты пути.
- Symlink и специальные файлы не поддерживаются.
- Корни нельзя удалять, переименовывать или переносить.
- Нельзя перезаписывать существующие данные.
- Проверка Exists не заменяет защиту от конкурентной перезаписи.
- Изменяющие HTTP-запросы требуют antiforgery.
- Не включай permissive CORS.
- Не записывай содержимое файлов в логи.
- Не заявляй защиту от враждебного локального процесса без
  соответствующего механизма и тестов.
- Недоступный корень не останавливает запуск: приложение работает
  с доступными корнями, недоступные помечаются и проверяются заново.

## Файловые операции

- Следуй семантике конфликтов и частичных ошибок из SPEC.
- Конфликт имени — всегда ошибка (409 / name_conflict), без автосуффиксов.
- Массовое удаление не поддерживается: удаляется только один объект.
- При копировании/перемещении все источники из одной родительской папки;
  порядок обработки — ordinal-сортировка по публичному пути.
- Сначала предварительная проверка (собирает все ошибки, при любой — стоп),
  затем выполнение до первой фактической ошибки.
- Сначала копирование и публикация, потом удаление источника move.
- Не делай fallback copy+delete на произвольную IOException.
- Временные объекты регистрируются.
- Нельзя удалять файлы только по совпадению с временным префиксом.
- Передача файлов на скачивание — потоковая, единым HTTP-ответом.
- Не выполняй синхронный полный обход дерева на UI-потоке компонента.

## SQLite

- Только параметризованные запросы.
- Нумерованные миграции.
- Короткие транзакции.
- Не держи транзакции во время файлового копирования.
- Не разделяй один SqliteConnection между конкурентными операциями.
- Изменения состояния задач сохраняются в БД.
- UI-уведомления не являются источником истины.
- При переподключении состояние полностью перечитывается из SQLite.
- Очистка истории удаляет только неактивные задачи (всех трёх видов),
  в рамках одной транзакции; файлы не изменяются.
- При недоступности/повреждении SQLite запуск приложения останавливается;
  автоматическое восстановление базы не выполняется.

## Тестирование

Добавляй тесты в той же итерации, что и поведение.

Используй:
- unit-тесты для чистой логики;
- временные каталоги для System.IO;
- временную SQLite для хранения;
- WebApplicationFactory для HTTP.

Не заменяй реальные файловые сценарии одними моками.

Базовые команды:

```text
dotnet build
dotnet test
docker build -t filemanager .
docker compose config
```

Linux-специфичные сценарии проверяй в Linux.
Если среда недоступна, записывай «не запускалось», а не «пройдено».

Не исправляй упавший тест удалением проверки или ослаблением
безопасности без объяснения причины.

## Документация

- Документация и ответы пользователю — на русском.
- Имена кода и API — на английском.
- Изменил публичный контракт или конфигурацию — обнови SPEC и README.
- Изменил схему БД — добавь миграцию.
- Новую зависимость добавляй с объяснением необходимости.
- Единственный roadmap — `docs/ROADMAP.md`; не создавай конкурирующие
  status/roadmap-файлы.
- Telemetry: OTLP exporter опционален; подключение к внешнему Collector —
  через стандартные переменные `OTEL_*`. Инструкция — в `docs/OPERATIONS.md`
  и `docs/SPEC.md` §18.

## Завершение сессии

Обнови `docs/PROJECT_STATE.md`:

- текущая итерация и её статус;
- выполненные пункты;
- незавершённые пункты;
- точные проверки и результаты;
- ограничения среды;
- принятые решения;
- известные дефекты;
- конкретный следующий шаг.

В финальном ответе кратко укажи:

1. Что реализовано.
2. Что проверено.
3. Что не проверено или заблокировано.
4. Что делать дальше.

Не объявляй итерацию завершённой при известных критичных дефектах.
