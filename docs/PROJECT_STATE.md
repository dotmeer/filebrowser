# Состояние проекта

Обновлено: 2026-11-14.

## Текущее состояние

Реализованы просмотр и поиск, виртуальный корень AllRoots, создание папок,
переименование, фоновые copy/move/delete, отмена и история в SQLite,
скачивание файлов и ZIP, предпросмотр, загрузка файлов, EN/RU, темы,
Docker и OpenTelemetry. Задание по ревью — [CODE_REVIEW_TASKS.md](CODE_REVIEW_TASKS.md).

Итерация 1 авторизации и пользователей принята после повторного ревью.

- `AUTH_MODE` (`ANONYMOUS` по умолчанию, `LOCAL`) читается при старте;
  пустое/неизвестное значение останавливает запуск. YAML, binding и mounts
  не менялись.
- Миграция 4 создаёт `users` и `sessions` поверх существующей БД; не более
  одной встроенной `admin` гарантирует частичный уникальный индекс.
- В `LOCAL` первый посетитель задаёт пароль `admin`; создание атомарно,
  конкурирующие POST не создают вторую учётку. Старые задачи и настройки
  настройке не мешают.
- Вход/выход, смена собственного пароля с текущим паролем, локальная команда
  `reset-admin-password` (пароль с консоли, только `admin`, отзыв его сессий).
  Пароли — хеши ASP.NET Core Identity со случайной солью.
- Cookie `HttpOnly`/`SameSite=Lax`/`Secure` при HTTPS; источник истины для
  полномочий — SQLite. Отзыв сессии действует на следующем HTTP-запросе или
  серверном действии Blazor, включая открытый circuit.
- В `LOCAL` HTML-страницы, файловые HTTP-маршруты и интерактивные действия
  требуют действующей учётки. Файловый HTTP без сессии отвечает
  `401/authentication_required`, без допуска — `403/access_denied`
  (ProblemDetails). Вход/настройка/публичные ресурсы/health доступны без
  сессии; временный пароль допускает только смену пароля и выход.
- С итерации 4 обычные учётные записи после смены временного пароля
  допускаются к рабочему UI и файловым операциям в пределах прав на корни
  (итерации 2–3). Страница `/users` доступна только `admin`; проверка
  выполняется до рендеринга и повторно в каждом действии.
- Выдача сессии при входе и первичной настройке привязана к версии пароля.
  Смена пароля проверяет также действующую сессию и атомарно отзывает старые
  сессии и создаёт новую. Возврат после входа ограничен локальными URL.
  Download и preview в `LOCAL` используют `Cache-Control: no-store`, включая
  частичные ответы на Range.

`ANONYMOUS` сохраняет прежнее поведение без входа, включая доступ ко всем
корням и общей истории; учётные записи и сессии в SQLite при переключении не
удаляются. В `ANONYMOUS` формы входа/настройки перенаправляют на `/`.

Итерация 2 с файловыми правами и защитой служебных каталогов принята после
повторного ревью.

- Миграция 5 создаёт `user_root_permissions` (`read|write` по имени корня,
  каскадное удаление вместе с учёткой). Отсутствие строки — нет доступа;
  `admin` всегда имеет полные права. Новое имя корня прав не получает.
- Матрица `read`/`write` применяется в сервисах чтения, поиска, ZIP, upload,
  записи и постановки задач: чтение — листинг/дерево/поиск/предпросмотр/
  download/ZIP; запись дополнительно — создание, rename, upload, delete и
  copy/move с корнем на любой стороне. `AllRoots` фильтрует корни, а путь под
  ним делегируется реальному корню с его правами.
- Закрытые по правам корни не попадают в `unavailableRoots`; туда попадают
  только видимые, но недоступные на ФС корни. При отсутствии видимых корней
  UI показывает пустое состояние.
- `ConfigPath`/`DatabasePath` внутри корня закрывают для обычных учёток
  непосредственные родительские каталоги (оба, если пути разные; весь корень,
  если файл лежит прямо в корне). Скрытая ветка отсутствует в листинге,
  дереве, поиске и выборе назначения; прямой запрос/операция, рекурсивный ZIP,
  copy/move/delete предка и rename предка отклоняются; соседний каталог
  остаётся доступен. `admin` видит служебные каталоги.
- При настройке служебного файла через ссылки защищены заданный и фактический
  родительские каталоги. Проверка учитывает цепочки промежуточных ссылок.
- Разрешение реального корня, проверка прав и запрета служебной ветки
  предшествуют проверкам существования и конфликтов при пользовательских
  операциях. Диспетчер отклоняет запрещённый путь до записи задачи в SQLite.
- ZIP-тикет привязан к ID создателя; чужой тикет ведёт себя как отсутствующий,
  погашение повторно проверяет актуальное право чтения. TTL, лимиты и
  повторное использование владельцем сохранены.
- UI отражает права: кнопки изменения и контекстное меню скрываются без
  `write`, выбор назначения показывает только доступные для записи корни.
  Актуальные права перечитываются на каждом новом действии.
- Точки исполнения задач принимают актора; передача сохранённого автора и
  повторные проверки во время длинной задачи реализованы в итерации 3.

Итерация 3 с авторством задач и отзывом прав принята после повторного ревью.

- Миграция 6 добавляет `tasks.author_user_id` (TEXT NULL, без внешнего ключа).
  Старые и анонимные задачи имеют `NULL`; удаление учётки сохраняет ID автора,
  результаты и регистрацию артефактов. Миграция применяется поверх БД версии 5.
- Новая задача copy/move/delete/upload сохраняет ID автора с сервера
  (`TaskDispatcher`/`UploadService`). Ограниченный актор без учётной записи
  не может создать задачу с `NULL`-автором.
- Видимость по автору применяется к активным задачам, истории, пагинации,
  чтению по ID, отмене, очистке истории, reconnect и сверке результата upload.
  Обычная учётка видит только свои задачи; `admin` и `ANONYMOUS` — все.
  Чужой ID ведёт себя как отсутствующий.
- Очистка истории обычной учётной записью удаляет только её неактивные задачи;
  `admin`/`ANONYMOUS` — все. Регистрация артефактов сохраняется.
- Ожидающая отмена upload до создания строки задачи хранится отдельно для
  каждой пары `uploadId` и инициатор. Заявка `admin`/системы действует для
  любого автора. Чужая заявка не заменяет отмену владельца и не присваивает ID.
- События задач содержат автора, события очистки — область истории. Чужая
  очистка не меняет страницу пользователя. Админ видит изменения в общей
  истории, глобальная очистка обновляет панели обоих типов.
- Worker перечитывает права автора из SQLite до старта (`failed/access_denied`
  без изменений на ФС при удалённой учётке или отозванных правах) и на
  безопасных точках: перед следующим объектом и перед публикацией copy/move,
  после регистрации артефакта delete, перед rename. При отказе неиспользованная
  регистрация снимается и исходник остаётся на месте. Завершённые объекты
  сохраняются, остатки —
  `not_processed/access_denied`, временные объекты очищаются или остаются
  зарегистрированными. Выход и смена пароля права принятой задачи не отзывают
  (`FileAccessService.CreateForTaskAsync` игнорирует `must_change_password`).
- upload перепроверяет права перед публикацией и периодически во время
  приёма тела (раз в секунду), поэтому остановившаяся передача не ждёт
  следующего байта; отзыв до публикации оставляет конечное имя свободным,
  удаляет временный файл и отвечает `403/access_denied`. `SQLITE_BUSY` и
  `SQLITE_LOCKED` откладывают проверку до следующего тика. При другой ошибке
  проверки ожидающее чтение тела прерывается, загрузка завершается ошибкой.

Отмена upload связана с задачей по `uploadId`. Одинаковый id не допускает
двух владельцев. Приём через PipeReader корректно прерывается даже при
остановившем передачу клиенте; при потере раннего HTTP-ответа окно загрузки
сверяет итог с SQLite через Blazor. Обычный обрыв не считается отменой.

Общий механизм синхронизации отмены и публикации не допускает конечный файл,
если отмена принята первой. После публикации результат элемента, итог задачи
и снятие регистрации артефакта фиксируются одной короткой SQLite-транзакцией.
При ошибке финализации опубликованный файл сохраняется; регистрация артефакта
остаётся, выполняется попытка зафиксировать failed. При продолжающейся
недоступности БД активная задача будет прервана при следующем запуске.

Итерация 4 с управлением пользователями реализована, замечания ревью
исправлены. Полная ручная приёмка открыта.

- `AuthService` допускает действующую обычную учётку к рабочему UI после смены
  временного пароля; файловые действия ограничены правами по корням. Ошибки
  прав по-прежнему `403/access_denied`, отсутствие сессии — `401`.
- `UserAdministrationService` проверяет `admin` по текущей сессии SQLite в
  каждом действии: список, создание, выдача прав, сброс пароля и удаление.
  Страница `/users` дополнительно закрыта `PageAccessMiddleware` до рендеринга
  для обычных учёток и в `ANONYMOUS`; в меню пункт виден только `admin`.
- Создание учётки и её прав выполняется одной транзакцией. Временный пароль
  обязателен, после входа разрешены только смена пароля и выход. Логин
  уникален без учёта регистра, `admin` зарезервирован, формат логина ограничен.
  Встроенную `admin` нельзя удалить, сбросить или изменить ей права.
- Сброс пароля ставит `must_change_password` и отзывает все сессии; удаление
  удаляет сессии и права каскадно. Старые задачи сохраняют ID автора, поэтому
  после пересоздания логина история остаётся у прежнего ID и видна только
  администратору.
- Повторный ввод временного пароля не снимает ограничение. Сохранение прав
  изменяет только настроенные корни. Записи временно убранного корня
  сохраняются и снова действуют при возврате того же имени.
- Глобальный язык в `LOCAL` меняет только `admin`; остальные видят действующий
  язык и меняют тему. В `ANONYMOUS` язык доступен без входа. Проверка языка
  выполняется серверным `LanguageSettingsService`, а не claim открытого circuit.

## Ограничения и следующий шаг

Отдельная регрессия для `SQLITE_BUSY`/`SQLITE_LOCKED` не добавлена. Сетевые
регрессии отзыва и ошибки чтения SQLite используют администратора в тестовой
БД. Ручные сценарии «Авторизация и пользователи» обновлены под фактический
интерфейс и переданы на приёмку.

Следующий шаг — завершить браузерные сценарии из MANUAL_TEST_SCENARIOS.
Повторная проверка не охватывала смену режима на одной БД, восстановление
администратора, полный обход форм EN/RU, служебные каталоги через UI,
историю двух пользователей после reconnect и отзыв во время пачки или
сетевой загрузки. Пункт «Пользователи и права доступа» уже удалён из ROADMAP.
