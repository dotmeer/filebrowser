Этот файл обновляется в конце каждой рабочей сессии,
включая незавершённую итерацию.

Допустимые статусы:

- не начата;
- в работе;
- заблокирована;
- завершена.

Итерация считается завершённой после реализации и выполнения её проверок.
Невыполненные проверки указываются явно.

Не хранить здесь секреты, токены и содержимое пользовательских файлов.

## Текущая итерация: I19 — Перевод UI-компонентов

панель задач, карточки задач, диалоги, layout, reconnect-модал, Home)
на инфраструктуру локализации I18: интерфейс целиком на двух языках,

- `TaskPresentation` переведён из статического класса в инстанс-сервис
  с внедрением `IStringLocalizer<SharedResources>`; зарегистрирован
  singleton в DI; локализуются подписи статусов, типов, статусов
  элементов и единицы байт; форматирование чисел осталось инвариантным;
  культурно-нейтральные члены (`GetPercent`, CSS-классы) остались
  статическими;
- потребители обновлены: `TaskCard`, `DestinationPicker` (включая
  подстановку подписи операции через `TypeLabel` вместо дублирующего
  `GetOperationLabel`), unit-тест презентации;
- `NotFound.razor` и `Error.razor` уже были на английском — изменений
  не потребовали;
- тесты: обновлены русские ожидания UI на английские
  (`FileSystemReadTests`, `TaskManagementTests` — презентация создаётся

- документация: ручной сценарий смены языка уточнён (переводится весь

## Итерация I18 — Инфраструктура мультиязычности

### Цель

Добавить английский (по умолчанию) и русский языки интерфейса; язык
выбирается на странице «Настройки» и хранится на сервере (SQLite);
локализовать UI страницы настроек и сообщения ошибок API. Перевод
остальных компонентов — отдельная итерация I19.

### Сделано

- миграция 2: таблица `app_settings(key, value)`; ключ `ui.language`,
  отсутствие строки означает `en`; сидирование не выполняется;
- `AppSettingsService` (singleton): синхронное чтение с кэшем и
  инвалидацией при записи, upsert в короткой транзакции; БД остаётся
  источником истины между перезапусками;
- `StoredLanguageProvider` + `UseRequestLocalization`: культура запроса
  определяется серверной настройкой (без заголовков/cookie браузера),
  default `en`, supported `en`/`ru`; динамический `lang` на `<html>`;
- resx-ресурсы `Localization/SharedResources.resx` (EN, базовый fallback)
  и `SharedResources.ru.resx`; маркерный класс `SharedResources` лежит в
  корневом namespace проекта (требование конвенции фабрики, D058);
- страница `/settings` полностью локализована и содержит форму выбора
  языка (`POST /settings/language`, antiforgery, валидация значения,
  redirect на `/settings` — полная навигация, т.к. культура Blazor
  circuit фиксируется при создании);
- `ApiExceptionMiddleware`: `title`/`detail` ProblemDetails через
  `IStringLocalizer` (маппинг «тип исключения → ключи ресурсов`);
  коды `code`/`traceId` и серверные логи не переводятся;
- middleware перенесён ВНУТРЬ `UseRequestLocalization`: иначе при перехвате
  исключения культура уже восстановлена и перевод не применялся (D059);
- фильтр antiforgery `/settings/language` возвращает 400 напрямую,
  а не бросает исключение мимо `/api`-обработчика (D060);
- тесты: unit `AppSettingsService` (default en, персистентность, кэш,
  отказ невалидного языка); Web (`Web application factory`):
  EN по умолчанию (`/settings`, `lang`, ProblemDetails), смена на RU
  через POST (страница + API), 400 без antiforgery и с невалидным языком;
  обновлён тест страницы настроек под английский по умолчанию;
  добавлен `PassthroughLocalizer` для прямого создания middleware в тестах;
- документация: SPEC §9.1/§9.6/§14/§16/§17, README, ручные сценарии;
  из ROADMAP удалён пункт про поддержку английского, добавлено
  направление «Изоляция тестов» (переход с процессных env-переменных

## Итерация I17 — Итеративный обход глубоких деревьев

### Цель

Устранить рекурсивный C#-обход файловых деревьев в операциях copy/move,
delete и cleanup временных объектов, не вводя пользовательский лимит глубины.

### Сделано

- добавлен общий внутренний `FileSystemTreeWalker.EnumerateValidated`:
  итеративный pre-order обход с явным стеком IEnumerator, проверкой
  symlink/unsupported-объектов и поддержкой CancellationToken;
- `FileTransferEngine.ScanObject` переведён на итеративный обход; BuildPlan
  теперь принимает CancellationToken и отменяет предварительный подсчёт;
- `FileTransferEngine.CopyDirectoryAsync` переведён на итеративный обход
  без рекурсивных вызовов;
- проверки деревьев перед удалением в `FileSystemWriteService` и
  `FileTransferEngine` переведены на общий walker;
- `TemporaryArtifactCleanupService` переведён на итеративную проверку
  зарегистрированных временных каталогов;
- из ROADMAP удалён пункт «ограничение глубины рекурсивного обхода»:
  вместо произвольного пользовательского лимита устранён рекурсивный
  обход в коде приложения;
- добавлены тесты: копирование глубокого дерева с контролем items/bytes,
  отмена предварительного сканирования, удаление глубокого дерева,
  cleanup глубокого зарегистрированного временного каталога;
- поведение публичного API не менялось.

### Осталось / не проверено

- Интерактивный UI не проверялся: изменение внутреннее, сценарии copy/move
  и delete покрыты автотестами.
- Экстремальные деревья на несколько тысяч уровней специально не
  генерировались: тесты используют безопасную для CI глубину 256 на Linux
  и 48 на Windows.

## Итерация I16 — Ограниченный пул блокировок назначений

### Цель

Устранить неограниченный рост статического реестра `DestinationLocks`
без небезопасной периодической очистки объектов синхронизации.

### Сделано

- статический `ConcurrentDictionary<string, object>` заменён массивом
  из фиксированных 256 объектов-блокировок;
- целевой физический путь отображается в lock-пул через беззнаковый хэш;
- память синхронизатора ограничена константой и не зависит от числа
  уникальных операций mkdir/rename;
- отдельная периодическая очистка не требуется;
- внутренний размер пула не вынесен в `config.yaml`;
- добавлены конкурентные тесты: при одновременном создании одного каталога
  и при одновременной публикации одного имени побеждает ровно одна операция,
  назначение не перезаписывается;
- из ROADMAP удалён пункт про периодическую очистку `DestinationLocks`.

### Осталось / не проверено

- Интерактивный UI не проверялся отдельно: изменение касается только
  внутренней синхронизации коротких операций `mkdir`/`rename`.

## Итерация I14 — Тема оформления и возврат из настроек

### Цель

Добавить на страницу `/settings` выбор светлой, тёмной или системной темы
и кнопку возврата на предыдущую страницу, не меняя серверную конфигурацию
и файловые операции.

### Сделано

- тема оформления: палитра MD3 для тёмной темы через
  `[data-bs-theme="dark"]` в `app.css`; Bootstrap 5.3.3 использует тот же
  атрибут для `form-control`, `table`, `form-check` и `color-scheme`;
  зашитые цвета (hover/disabled/scrim/тени) вынесены в CSS-переменные;
- выбор темы: нативные радиокнопки «Системная / Светлая / Тёмная»
  на `/settings`; значение хранится в `localStorage`
  (`filebrowser.theme`), по умолчанию — `system`; режим `system` следует
  `prefers-color-scheme` и реагирует на его изменение;
- применение темы выполняется синхронным скриптом в `<head>` до отрисовки
  body — без вспышки светлой темы; страница `/settings` осталась статической
  (без Blazor circuit), переключение работает на чистом JS;
- enhanced navigation Blazor затирает `data-bs-theme` на `<html>` серверной
  разметкой; тема повторно применяется по `enhancedload`, подписка идёт и на
  `document`, и на `Blazor`, с повторным применением в `requestAnimationFrame`;
  выбор радиокнопок синхронизируется после каждой навигации;
- кнопка «Назад» возвращает по истории браузера. Проверка «предыдущая запись
  внутри приложения» использует Navigation API (Chromium), затем
  `document.referrer`, затем маркер в `sessionStorage`; при прямом открытии
  `/settings` без истории выполняется переход на `/`;
- в тёмной теме приведены к палитре reconnect-модал и полоса
  `#blazor-error-ui` (иначе светлый фон сочетался со светлым текстом);
- обновлены SPEC §9.1/§9.6, README, ручные сценарии и тест страницы
  настроек.

### Осталось / не проверено

- Визуальная проверка скриншотами не выполнялась: окно браузера в этой
  сессии не было видимым; проверка шла через DOM и вычисленные стили.
- Контраст проверен выборочно (фон/текст страниц, диалог, поля ввода,
  таблица, подсказки), без полного аудита всех состояний.
- Автоматического теста JS-логики темы нет (в проекте нет JS-тестов);
  покрыт серверный рендер страницы настроек.

## Итерация I13 — Интерактивная приёмка UI и фикс Docker-сборки

### Цель

Проверить интерактивный UI в реальном браузере через расширение browse,
устранить найденные дефекты, не меняя функциональность MVP.

### Сделано

- **BUG-001 (Docker/Blazor).** В контейнере `/_framework/blazor.web.js`
  отдавался 404: интерактивность Blazor не подключалась (кнопки, диалоги,
  меню не работали). Причина: `dotnet restore` в Dockerfile выполнялся при
  наличии только csproj, затем `dotnet publish --no-restore` — манифест
  статических ресурсов .NET 10 терял JS фреймворка Blazor. Исправлено
  повторным `dotnet restore` после `COPY . .` до publish (D054);
  проверено: `_framework/blazor.web.js` → 200;
- **BUG-002 (панель задач).** Уведомление об изменении задачи, пришедшее во
  время выполняющегося refresh, отбрасывалось: карточка завершённой задачи
  оставалась в «Активных», а список файлов не обновлялся после copy/move.
  Заменено на асинхронный цикл с флагом `pending`: изменения во время
  refresh гарантируют ещё один проход (D055);
- `aria-expanded` бургер-кнопки теперь рендерится как `true`/`false`;
- полная интерактивная приёмка в контейнере через расширение browse:
  аппбар и бургер-меню, «Настройки», разделители (ресайз и минимальные
  ширины 220/520/300px), состояния кнопок по выделению, mkdir, rename,
  конфликт имён, download (200, 221 Б, `octet-stream`, Content-Disposition),
  copy и move с выбором назначения и автообновлением панели/списка,

## Известные дефекты

Нет открытых дефектов продукта.
Это не означает, что приложение проверено.

Флейк тестовой инфраструктуры (2026-11-07, I14): при одном прогоне
`MoveEndpoint_QueuesAndCompletesMoveWithAntiforgery` упал с «Файл
конфигурации не найден». Тест меняет процессные переменные
`ConfigPath`/`DatabasePath`, а xUnit выполняет классы параллельно;
соседний тест может увидеть чужой/удалённый путь. Повторный прогон —
109/109. Это дефект изоляции тестов, не продукта; в I14 не исправлялся.

BUG-001 (исправлен 2026-11-07, I13)
  - серьёзность: критичная (весь интерактивный UI в контейнере);
  - симптом: в Docker `GET /_framework/blazor.web.js` → 404, Blazor circuit
    не подключается, кнопки/диалоги/меню не работают;
  - воспроизведение: `docker compose up --build`, открыть `/browse`;
  - причина: Dockerfile выполнял restore с одними csproj, затем
    `dotnet publish --no-restore`; манифест статических ресурсов терял
    JS фреймворка Blazor;
  - ожидаемое поведение: скрипт отдаётся 200, UI интерактивен;
  - затронутая итерация: Dockerfile с I01, выявлено в I13;
  - исправление: повторный `dotnet restore` после `COPY . .` (D054).

BUG-002 (исправлен 2026-11-07, I13)
  - серьёзность: средняя (UI-состояние расходилось с SQLite);
  - симптом: завершённая задача оставалась в «Активных», список файлов
    не обновлялся после copy/move до ручного refresh;
  - причина: уведомление, пришедшее во время выполняющегося refresh,
    отбрасывалось флагом `_refreshScheduled`;
  - исправление: цикл refresh с флагом `pending` — повторный проход при
    изменениях во время refresh (D055).

В S009 найден и исправлен дефект: в Production ошибки API перехватывались
generic exception handler раньше `ApiExceptionMiddleware` и возвращались как
`500` HTML вместо ProblemDetails. Причина — порядок middleware; исправление
покрыто тестом `ApiErrors_InProduction_KeepProblemDetailsContract`.

В S010 исправлен платформенный дефект теста symlink: на Linux рядом с `link`
находился `target`, а тест ожидал ровно одну запись. Это была ошибка теста,
а не продукта; проверка `unsupported` сохранена.

В S012 (I09) найден и исправлен дефект UI: `SelectedEntry` вычислялся через
`SingleOrDefault`, который бросает исключение при двух и более выбранных
объектах. Теперь переименование и удаление доступны только при ровно одном
выбранном объекте, а копирование/перемещение — для нескольких.
