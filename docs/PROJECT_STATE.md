## Текущая итерация: I11 — Наблюдаемость, документация, приёмка

### Цель

Закрыть приёмку MVP: добавить структурированные логи и корреляцию по
`traceId`, базовую OpenTelemetry-инструментацию, spans задач, метрики очереди
и выполнения, опциональный OTLP exporter через стандартные `OTEL_*`
переменные, актуализировать Docker/README и провести контейнерные приёмочные
проверки без добавления roadmap-функций.

### Сделано

- добавлены OpenTelemetry-пакеты и регистрация `AddFileBrowserObservability`:
  resource `service.name=dotmeer.filebrowser`, tracing ASP.NET Core/HttpClient,
  custom `ActivitySource`, metrics meter, ASP.NET Core/HttpClient/runtime
  instrumentation; OTLP exporter подключается только при заданном endpoint,
  без endpoint приложение работает без внешних observability-зависимостей;
  поддержан `OTEL_SDK_DISABLED=true`;
- JSON console logs с UTC-временем и scopes; `ActivityTrackingOptions`
  добавляет trace/span/parent id в логи; startup-лог фиксирует сервис,
  версию, `workers` и публичные имена корней, но не физические пути;
- `ApiExceptionMiddleware` теперь использует `Activity.Current.TraceId` при
  наличии trace, добавляет scope с `TraceId`/методом/путём, логирует 5xx с
  исключением, а ожидаемые 4xx — предупреждением без stack trace;
  `ProblemDetails.traceId` соответствует логам;
- `TaskExecutorHostedService` создаёт span `filebrowser.task.execute` с
  публичными тегами задачи и состоянием `completed`/`failed`; `TaskDispatcher`
  и worker-ы публикуют метрики очереди, старта, завершения, отказа,
  длительности, обработанных байтов и объектов;
- `TaskMetrics` покрывает `enqueued`, `rejected`, `started`, `finished`,
  `queue_depth`, `duration`, `bytes_processed`, `items_processed`;
- добавлены `ObservabilityTests`: проверка метрик и интеграционная проверка
  span-а/метрик при выполнении задачи; общий suite вырос до 109 тестов;
- README дополнен разделами наблюдаемости, OTLP-инструкции для внешнего
  Collector, ручной приёмкой, ограничениями symlink/cross-device/сторонних
  изменений, backup `/config`; Compose содержит закомментированный пример
  `OTEL_*` без изменения default runtime-конфигурации.

## Подтверждённые возможности

- Решение `dotmeer.filebrowser.slnx` собирается без ошибок и предупреждений
  (SDK 10.0.401, net10.0);
- YAML-конфигурация загружается однократно при старте; отсутствующая или
  невалидная конфигурация останавливает запуск, а недоступный корень — нет;
- общий resolver принимает только публичные `root + path`, проверяет границы
  корня, symlink в существующих компонентах и отклоняет сегменты
  `.filebrowser-*`; внутренний путь используется только очисткой временных
  объектов;
- `GET /healthz` отвечает `200` с телом `{"status":"ok"}` — подтверждено
  тестом WebApplicationFactory, включая недоступный корень;
- GET `/api/fs/roots` и `/api/fs/list` возвращают публичные DTO без
  физических путей; каталог сортируется по правилам SPEC;
- API ошибки возвращаются как ProblemDetails с `code` и `traceId`, в том числе
  в Production (проверено тестом и контейнерным smoke-тестом);
- `/browse` рендерит прямой URL, листинг, дерево и панель задач; дерево
  загружает потомков только при раскрытии соответствующего узла;
- простые изменения и постановка copy/move доступны через общие сервисы,
  Minimal API и Blazor UI; изменяющие endpoint требуют antiforgery, конфликт
  имени простой операции — `409/name_conflict`;
- SQLite-модель задач, миграции, FIFO bounded queue, workers и API задач
  реализованы;
- `POST /api/tasks/copy` ставит задачу, выполняет предварительную проверку,
  копирует файлы и каталоги между корнями, публикует результат без перезаписи
  и сохраняет агрегированный результат по верхнеуровневым объектам;
- `POST /api/tasks/move` ставит задачу, выполняет быстрый rename в пределах
  одной файловой системы, использует copy + delete только при подтверждённом
  EXDEV и сохраняет частичный результат при ошибке удаления источника;
- copy/move-конфликт имени отражается как ошибка задачи `name_conflict`, а не
  HTTP 409; существующие данные не изменяются;
- `DELETE /api/tasks/history` с antiforgery удаляет только неактивные задачи в
  одной транзакции, каскадно удаляет результат и возвращает `deletedCount`;
- серверный `TaskNotificationService` публикует изменения задач; `TaskPanel`
  подписывается, отписывается при уходе со страницы и перечитывает состояние
  из SQLite при подключении и переподключении;
- панель показывает активные задачи отдельно от истории, историю страницами по
  50, состояния scanning/running, неопределённый прогресс, проценты, скорость,
  счётчики и частичные результаты по верхнеуровневым объектам;
- окно выбора папки назначения использует ленивое дерево и запрещает текущую
  папку, исходные объекты и их потомков;
- переименование и удаление доступны ровно для одного выбранного объекта;
- `GET /api/fs/download` отдаёт один обычный файл потоком без буферизации:
  `application/octet-stream`, `Content-Disposition: attachment` (не-ASCII имена
  через `filename*=UTF-8''...`), `Content-Length`, Range → `206` с
  `Content-Range`; GET не требует antiforgery; папка/корень →
  `400/invalid_request`, отсутствующий объект → `404/not_found`, symlink →
  `422/unsupported_object`, `.filebrowser-*`/traversal → `400`;
- ошибка чтения потока после начала ответа перевыбрасывается middleware
  (ProblemDetails не пишется поверх начатого ответа);
- кнопка «Скачать» в `/browse` доступна только при выборе ровно одного файла;
  ссылка ведёт на `/api/fs/download` и открывается навигацией браузера;
- логи приложения пишутся в JSON console с UTC-временем и scopes; startup,
  постановка задач, файловые/API-ошибки доступны в контейнерном stdout;
- `ProblemDetails.traceId` коррелирует с JSON-логами; в smoke-тесте traceId
  отказа download папки найден в логах контейнера;
- OpenTelemetry tracing включает ASP.NET Core/HttpClient и span
  `filebrowser.task.execute`; metrics meter публикует счётчики задач,
  queue depth, длительность, байты и элементы; runtime/ASP.NET/HttpClient
  метрики включены; OTLP exporter включается только через `OTEL_*` endpoint;
- тестовый проект работает: `dotnet test` — 109/109 на Windows и 109/109 в
  Linux-контейнере, включая observability, download и symlink; cross-device
  ветки покрыты unit-тестами, а реальный cross-device повторно подтверждён в
  I08, не в I11;
- Docker image `filemanager-i11` собран и прошёл контейнерный smoke test:
  health/list/mkdir/rename/copy/move/conflict/restart/download/Range/history
  clear/app.db/non-root/traceId в логах; `docker compose config` проходит.
- Контейнер пишет ключи Data Protection в непостоянный каталог пользователя и
  предупреждает, что они не зашифрованы. При пересоздании контейнера открытые
  browser sessions могут потребовать обновления страницы; постоянное хранение
  ключей в MVP не настроено.

## Известные дефекты

Нет открытых дефектов.
Это не означает, что приложение проверено.

В S009 найден и исправлен дефект: в Production ошибки API перехватывались
generic exception handler раньше `ApiExceptionMiddleware` и возвращались как
`500` HTML вместо ProblemDetails. Причина — порядок middleware; исправление
покрыто тестом `ApiErrors_InProduction_KeepProblemDetailsContract`.

В S010 исправлен платформенный дефект теста symlink: на Linux рядом с `link`
находился `target`, а тест ожидал ровно одну запись. Это была ошибка теста,
а не продукта; проверка `unsupported` сохранена.

В S012 (I09) найден и исправлен дефект UI: `SelectedEntry` вычислялся через
`SingleOrDefault`, который бросает исключение при двух и более выбранных
объектах. Теперь переименование и удаление доступны только при ровно одном
выбранном объекте, а копирование/перемещение — для нескольких.
