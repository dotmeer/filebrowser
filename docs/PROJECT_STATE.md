## Итерация I24 — Удаление внешнего HTTP API

### Цель

Убрать публичный HTTP API целиком (решение пользователя): приложение
работает в изолированной доверенной сети для нечастой ручной работы,
внешних клиентов (скрипты, CLI, интеграции) не предполагается. Наружу
остаются только: `GET /api/fs/download` (кнопка «Скачать» в UI ведёт
на него навигацией браузера) и health-checks для эксплуатации.

### Сделано

- Удалены эндпоинты: `FileSystemEndpoints` (roots/list/search/mkdir/
  rename/delete), `TaskEndpoints` (все `/api/tasks/*`), `SettingsEndpoints`
  (`POST /settings/language`), `HealthEndpoints` (`/healthz`),
  `ApiExceptionMiddleware` и все CSRF-фильтры (`RequireCsrfValidation`,
  `AntiforgeryRequestRejectedException`, DTO `MkdirRequest` и др.).
- Создан `Endpoints/DownloadEndpoint.cs` — единственный сохранённый
  эндпоинт: `GET /api/fs/download` (виртуальный корень, поток, Range,
  Content-Disposition). Ошибки маппятся локально в delegate в тот же
  ProblemDetails-контракт (`code`, `traceId`, локализованные title/detail,
  без физических путей) с использованием ключей `Error_*`; middleware
  больше не нужен.
- Health: стандартный `AddHealthChecks()` + `MapHealthChecks("/health/live")`
  и `("/health/ready")` (liveness/readiness для k8s; зарегистрированных
  проверок нет — 200, как только приложение отвечает).
- `Settings.razor`: смена языка — обработчик Blazor
  (`AppSettingsService.SetLanguageAsync` + полная перезагрузка страницы
  для применения культуры middleware локализации).
- Antiforgery DI/middleware и скрытая форма в `App.razor` сохранены —
  они часть инфраструктуры Blazor Web App.
- OTEL: `AddHttpClientInstrumentation` и пакет
  `OpenTelemetry.Instrumentation.Http` удалены; AspNetCore-инструментация
  сохранена (покрывает Blazor и скачивание).
- resx: удалены ключи `Error_NameConflict_*`, `Error_Antiforgery_*`,
  `Error_TaskNotFound_*`, `Error_TaskQueueFull_*` (использовались только
  удалённым middleware).
- Тесты: удалены HTTP-специфичные (~60): `SearchEndpointTests`,
  `VirtualRootEndpointTests`, HTTP-части read/write/task-тестов,
  antiforgery-хелперы; `DownloadTests` → `DownloadEndpointTests`
  (перенесён тест скачивания через виртуальный корень, добавлен
  Production-контракт); `HealthzTests` → `HealthCheckTests`;
  покрытие чтения перенесено на unit-вызовы сервисов
  (`FileSystemReadServiceTests`), добавлен `CreateDirectory_ReturnsPublicReference`.
- Документация: SPEC §4, §5.3, §8.4, §9.6, §15, §16, §17, §19, §22;
  README (раздел «HTTP API» → «HTTP-интерфейс»); OPERATIONS.md

## Итерация I23-1 — Виртуальный корень: серверная часть

### Цель

Реализовать серверную поддержку виртуального корня `AllRoots` (SPEC §7.1,
§10.6, §16): объединение всех настроенных корней для чтения (list, search,
download) с запретом изменяющих операций. Backend-only: UI (дерево «Все
корни», уведомления о недоступных корнях) — отдельная итерация I23-2.

### Сделано

- `FileSystem/VirtualRoot.cs`: константа `VirtualRootName = "AllRoots"`
  (имя намеренно вне алфавита имён корней `[a-z0-9_-]`, коллизия с
  конфигурацией невозможна; правила валидации конфигурации не менялись),
  `IsVirtualRoot` (ordinal, только точное имя — реальный корень `allroots`
  в нижнем регистре остаётся доступным как обычный), `SplitPath`
  (первый сегмент → имя реального корня, остаток пути);
- запрет мутаций в одном месте: `PathResolver.GetRoot` отклоняет
  `root=AllRoots` с `InvalidFileSystemRequestException` →
  `400/invalid_request` через существующий middleware. Проверено по коду,
  что обходных путей нет: mkdir/rename/delete идут через
  `ResolveExisting`/`ResolveNewChild`, copy/move разрешают источники и
  назначение через `ResolveExisting` в `FileTransferEngine.BuildPlan`;
  физические пути не раскрываются (русское сообщение исключения, без путей);
- `FileSystemReadService.List`: `root=AllRoots`, пустой `path` — настроенные
  корни как каталоги (`kind="directory"` для доступных, `"unsupported"` для
  недоступных; доступность — тем же `IsAvailable`, что `/api/fs/roots`,
  без раскрытия причин; `size=null`; `modifiedAtUtc` — время изменения
  физического каталога корня или `null`; сортировка ordinal по имени);
  `path=<realRoot>/<rest>` — делегирование в `List(FileRef(realRoot, rest))`
  с префиксом `<realRoot>/` у `path` каждого элемента (`name` не меняется),
  ответ с `Root="AllRoots"` и исходным `path`. Неизвестный первый сегмент →
  `404/not_found` (делегирование в `GetRoot`), `AllRoots/<root>/<file>` →
  `400/invalid_request` («не каталог»), `.filebrowser-*` под виртуальным
  корнем отклоняется делегированием в реальный resolver;
- `FileSystemReadService.OpenFile`: remap первого сегмента в реальный корень,
  все проверки resolver-а сохраняются (symlink, `.filebrowser-*`, границы);
- `FileSystemSearchService.Search`: обход одного корня вынесен в приватный
  `WalkSingleRoot` (общие на весь запрос лимит результатов, бюджет 60 с и
  счётчик узлов; досрочная остановка → `truncated: true`); `root=AllRoots`,
  пустой `path` — последовательный обход каждого доступного корня по порядку
  конфигурации, недоступные пропускаются и собираются в `UnavailableRoots`;
  пути хитов получают префикс `<realRoot>/`; сортировка — ordinal по имени
  корня первым ключом, затем существующая (каталоги→файлы→unsupported,
  ordinal по имени); `path=<realRoot>/<rest>` — делегирование одному корню
  с префиксом хитов; недоступность всех корней → пустой `results` +
  `unavailableRoots`, не ошибка;
- `SearchResultDto` дополнен `UnavailableRoots` (init, по умолчанию пустой
  массив; для реальных корней сериализуется `[]`); сериализация
  camelCase `unavailableRoots`; строки уведомления для UI — I23-2;
- `FileEntryDto.ModifiedAtUtc` стал `DateTimeOffset?` (недоступный корень
  верхнего уровня не имеет времени изменения); потребитель `Browse.razor`
  адаптирован минимально: ячейка «Изменён» рендерит `RenderFragment`
  (`—` при `null`; для реальных листингов поведение и разметка прежние
  `<time class="local-time">`);
- endpoints (`FileSystemEndpoints.cs`) не менялись: виртуальный корень
  проходит через те же `root`/`path`; маппинг ошибок прежний
  (404 `not_found`, 400 `invalid_request`; 503 `root_unavailable` в
  виртуальном режиме не возникает — недоступные корни пропускаются);
- `FileSystemSearchService` получил `FileBrowserConfiguration` в конструктор
  (итерация корней для виртуального поиска); регистрация в DI не менялась;
- тесты (19 новых, итого 230): `VirtualRootServiceTests` (13; сервисы на
  временных каталогах с корнями alpha/beta/offline): верхний уровень list
  (корни как каталоги, `offline` → `unsupported`, `modifiedAtUtc=null`),
  list под корнем с префиксами путей, неизвестный сегмент → `not_found`,
  файл вместо каталога → `invalid_request`, download через AllRoots ==

## Известные дефекты

Нет открытых дефектов продукта.
Это не означает, что приложение проверено.

Флейк тестовой инфраструктуры (2026-11-07, I14): при одном прогоне
`MoveEndpoint_QueuesAndCompletesMoveWithAntiforgery` упал с «Файл
конфигурации не найден». Тест менял процессные переменные
`ConfigPath`/`DatabasePath`, а xUnit выполняет классы параллельно;
соседний тест мог увидеть чужой/удалённый путь. Повторный прогон —
109/109. Это дефект изоляции тестов, не продукта; исправлен в I21:
переход на per-host конфигурацию `TestHostFactory` (`UseSetting`) и
включение `CopyTaskExecutorTests`/`MoveTaskExecutorTests` в
последовательную коллекцию.

BUG-001 (исправлен 2026-11-07, I13)
  - серьёзность: критичная (весь интерактивный UI в контейнере);
  - симптом: в Docker `GET /_framework/blazor.web.js` → 404, Blazor circuit
    не подключается, кнопки/диалоги/меню не работают;
  - воспроизведение: `docker compose up --build`, открыть `/browse`;
  - причина: Dockerfile выполнял restore с одними csproj, затем
    `dotnet publish --no-restore`; манифест статических ресурсов терял
    JS фреймворка Blazor;
  - ожидаемое поведение: скрипт отдаётся 200, UI интерактивен;
  - затронутая итерация: Dockerfile с I01, выявлено в I13;
  - исправление: повторный `dotnet restore` после `COPY . .` (D054).

BUG-002 (исправлен 2026-11-07, I13)
  - серьёзность: средняя (UI-состояние расходилось с SQLite);
  - симптом: завершённая задача оставалась в «Активных», список файлов
    не обновлялся после copy/move до ручного refresh;
  - причина: уведомление, пришедшее во время выполняющегося refresh,
    отбрасывалось флагом `_refreshScheduled`;
  - исправление: цикл refresh с флагом `pending` — повторный проход при
    изменениях во время refresh (D055).

В S009 найден и исправлен дефект: в Production ошибки API перехватывались
generic exception handler раньше `ApiExceptionMiddleware` и возвращались как
`500` HTML вместо ProblemDetails. Причина — порядок middleware; исправление
покрыто тестом `ApiErrors_InProduction_KeepProblemDetailsContract`.

В S010 исправлен платформенный дефект теста symlink: на Linux рядом с `link`
находился `target`, а тест ожидал ровно одну запись. Это была ошибка теста,
а не продукта; проверка `unsupported` сохранена.

В S012 (I09) найден и исправлен дефект UI: `SelectedEntry` вычислялся через
`SingleOrDefault`, который бросает исключение при двух и более выбранных
объектах. Теперь переименование и удаление доступны только при ровно одном
выбранном объекте, а копирование/перемещение — для нескольких.
