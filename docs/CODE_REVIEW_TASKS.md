## Исправления

### C01. Зафиксировать назначение каждого загружаемого файла — высокий приоритет

**Места:** `wwwroot/upload.js`: enqueue/start/setContext;
`Components/Pages/Browse.razor`: настройка контекста загрузки.

**Дефект:** start берёт root/path из изменяемого state.context и перед check,
и после await перед POST. При навигации очередь или уже проверенный файл
могут отправиться в другую папку.

**Изменение:** скопировать root/path в каждый элемент очереди при enqueue;
check и POST используют только этот снимок. Навигация влияет лишь на новые
элементы. Сохранить лимит двух параллельных отправок и текущую семантику
ухода со страницы/dispose. После завершения обновлять актуальный листинг,
не возвращая пользователя насильно в исходную папку.

**Готово, когда:**
- Автопроверка JS/браузера: выбрать ≥3 файлов в A, пока первые отправляются
  перейти в B; все исходные файлы попадают только в A, новые выбранные — в B.
- Отдельная проверка задерживает ответ check, меняет навигацию и подтверждает,
  что последующий POST имеет то же назначение, что check.
- Проверены путь под AllRoots, отмена ожидающего файла и dispose;
  после ухода не запускаются забытые элементы очереди.

### C02. Сохранить регистрацию артефактов при очистке истории — высокий приоритет

**Места:** `Tasks/TaskDatabase.cs`, `TaskRepository.DeleteInactiveAsync`,
модель TemporaryArtifact в `Tasks/FileTask.cs`, `TemporaryArtifactCleanupService`,
`TaskManagementTests.HistoryCleanup_DeletesOnlyInactiveTasksWithTheirItemsAndArtifacts`.

**Дефект:** temporary_artifacts имеет FK ON DELETE CASCADE на tasks.
Удаление failed/interrupted/completed-задачи теряет запись остатка на диске.
Существующий тест ошибочно требует исчезновения такой регистрации.

**Изменение:** отделить срок жизни регистрации от истории. Предпочтительный
минимальный вариант — новая нумерованная миграция: nullable task_id с
ON DELETE SET NULL, адаптация модели/чтения, cleanup без обязательной задачи.
Сохранить id, root/path, время и все существующие регистрации. Применённые
миграции 1/2 не переписывать. Если выбран другой вариант, он обязан сохранять
все гарантии ниже и быть объяснён в итоговом отчёте.

**Готово, когда:**
- Реальный временный файл/каталог зарегистрирован у неактивной задачи;
  DeleteInactive удаляет задачу и task_items, но не файл и не регистрацию.
- После открытия новой TaskDatabase/Repository (имитация рестарта) cleanup
  удаляет остаток и только затем регистрацию. Чужой похожий префикс не тронут.
- При недоступном корне/ошибке удаления запись сохраняется, повторная очистка
  после восстановления доступа успешна. Активные задачи и их записи сохранены.
- Тест обновления существующей БД с миграцией 2 сохраняет задачи/артефакты,
  foreign_key_check чистый, повторная миграция идемпотентна.
- Исправлен старый тест с объяснением, почему прежнее ожидание было дефектом;
  очистка истории по-прежнему удаляет ВСЕ неактивные задачи, не только без остатков.

### C03. Реально отклонять специальные файлы в Linux — высокий приоритет

**Места:** `FileSystem/PathInspection.cs`, `FileSystemTreeWalker.cs`,
классификация в `FileSystemReadService.cs` и `FileSystemSearchService.cs`.

**Дефект:** FileAttributes.Device не определяет Unix-тип FIFO/socket/device.
В .NET Unix GetAttributes выставляет лишь часть файловых атрибутов; источник:
https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/System.Private.CoreLib/src/System/IO/FileStatus.Unix.cs

**Изменение:** единая проверка фактического типа объекта для всех операций
и листинга; поддерживаются только regular file/directory, symlink отдельно
запрещён. При необходимости — небольшой изолированный Linux-адаптер,
без неподтверждённых предположений о ABI/размерах native struct. Не открывать
FIFO для определения типа (это само может зависнуть). Сохранить Windows-путь.
Поиск пропускает неподдерживаемые узлы, валидирующий walker отклоняет их.

**Готово, когда:**
- Linux-тесты на реальных FIFO и Unix socket: resolver/download/preview,
  copy/move/delete и ZIP не читают/изменяют их, возвращают unsupported;
  поиск пропускает, листинг помечает неподдерживаемыми.
- Сценарий с доступным устройством проверен безопасно (например, test root
  на /dev для read-only проверки resolver); системные устройства не удаляются.
- Нет зависаний: внешняя граница времени теста и cleanup работают даже при
  регрессии. Unit-моки/Windows-прогон не заменяют Linux-воспроизведение.
- Обычные файлы/каталоги и существующие symlink-тесты работают по-прежнему.

- Прямой URL, prerender, AllRoots, лимит/бюджет и существующие search-тесты сохранены.

### C05. Проверять фактическую файловую систему назначения — средний приоритет

**Места:** `Tasks/FileTransferEngine.cs`: IsFreeSpaceCheckRequired/GetAvailableFreeSpace;
`Uploads/UploadService.cs`: EnsureFreeSpace; `FreeSpaceCheckTests.cs`.

**Дефект:** Path.GetPathRoot на Unix даёт `/` для разных mounts. Место
опрашивается у `/`, межтомовый move ошибочно считается внутритомовым.

**Изменение:** общий механизм опроса свободного места по фактическому пути
назначения и определения одной ФС (не по строковому `/`). Используй
проверенные API/небольшой ОС-адаптер. Невозможность опроса остаётся advisory;
не заменяй её ложным «места нет». Cross-device fallback по исключению сохранить.

**Готово, когда:**
- Linux-интеграция с двумя реальными mounts (например, tmpfs и обычная ФС)
  различает move внутри ФС и между ФС; не опирается только на mock DriveInfo.
- Малое свободное место назначения при достаточном месте `/` даёт отказ
  upload/copy/межтомового move до записи; внутритомовый rename не требует
  размера копии. Ошибка опроса не блокирует операцию.
- Windows-проверки сохранены; для mount-сценария указан конкретный способ запуска.

### C06. Согласовать отмену в окне загрузки и в задачах — средний приоритет

**Места:** `wwwroot/upload.js`: cancel/start; `Components/Pages/Browse.razor`;
`Endpoints/UploadEndpoint.cs`, `Tasks/TaskCancellation.cs`.

**Дефект:** xhr.abort означает серверу сетевой обрыв; браузер пишет cancelled,
а БД — failed/upload_aborted. Это не пользовательская отмена через сервис задач.

**Изменение:** надёжно связать элемент браузерной очереди с конкретной
upload-задачей и передавать пользовательскую отмену через Blazor в общий
TaskCancellationService. Не сопоставлять задачи лишь по имени/пути: возможны
одновременные клиенты. Корреляция должна быть известна до отмены, переживать
гонку создания задачи и отмены, не оставлять вечный in-memory реестр.
Если вводится идентификатор в query, валидировать его, не позволять повторному
upload переиспользовать чужую/существующую задачу. Без нового cancel HTTP API.
При отмене до старта POST задача не требуется. Обрыв без явного действия
пользователя по-прежнему failed/upload_aborted. Не считать любой disconnect
пользовательской отменой.

**Готово, когда:**
- Отмена ожидания/check/начала POST/середины передачи проверена; UI и SQLite
  согласованы, после отмены до публикации нет конечного файла/остатка.
- Отмена из панели задач также обновляет окно загрузки; повторная отмена безопасна.
- Закрытие вкладки/обрыв без отмены даёт failed/upload_aborted, shutdown — interrupted
  после рестарта. Одинаковые имена от двух клиентов не путают отменяемую задачу.
- Проверены отсутствие/дублирование/невалидность корреляции, если она добавлена;
  существующий raw POST и antiforgery-контракт сохранены, расширения документированы.

### C07. Исправить гонку публикации и финализации upload — средний приоритет

**Места:** `Uploads/UploadService.cs`: PublishAsync/AbortAsync;
`Endpoints/UploadEndpoint.cs`, переходы/результаты в TaskRepository.

**Дефект:** чтение статуса и переход completed разделены; отмена между ними
может вызвать исключение и AbortAsync после уже успешной публикации.
PublishAsync также не сообщает эндпоинту о cancelled, тот возвращает 201.

**Изменение:** проверяемая конкурентно-безопасная финализация и явный результат
публикации для эндпоинта. Разделить «файл уже опубликован» и «приём неуспешен»:
не переписывать completed-элемент как failed/not_processed после публикации.
201 — completed; победившая отмена — 409/upload_cancelled. Если отмена принята
после публикации, но до completed, сохранить файл/успешный элемент, задача
cancelled по SPEC §13.8. После completed отмена — no-op. Не держать SQLite
транзакцию во время файловой записи/публикации.

**Готово, когда:**
- Детерминированные проверки с барьерами (не sleep в надежде на гонку):
  отмена до публикации; после публикации до финала; между чтением статуса
  и переходом; после completed. Совпадают файл, статус задачи, элемент и HTTP.
- Нельзя получить 500 только из-за гонки отмены, потерять опубликованный файл
  или пометить его «не обработан». Метрики фиксируют один итог.
- Конфликт финального имени, ошибка записи и ошибка SQLite после публикации
  не удаляют чужой/опубликованный файл; регистрация остатка не теряется.
- Повторная отмена/одновременная очистка истории не оставляет активную задачу
  без исполнителя; тесты C02/C06 сохранены.

### C08. Применять лимиты ZIP при сборе верхнего уровня — средний приоритет

**Места:** `Archive/FileSystemArchiveService.cs`: Plan/ResolveTopLevelItems.

**Дефект:** полный список верхнего уровня собирается до проверок времени,
числа записей и cancellation; большая плоская папка может съесть память/время.

**Изменение:** ленивый/ограниченный сбор, проверки бюджета и cancellation
во время перечисления и обработки выбранных имён; лимиты применяются до
накопления неограниченного списка. Время планирования учитывает весь обход.
Сохранить структуру, детерминированную сортировку итогового ограниченного плана
и исключение временных объектов.

**Готово, когда:**
- Большой плоский каталог превышает MaxEntries и останавливает планирование
  на границе лимита, а не после накопления всего каталога.
- Отмена и TimeProvider-бюджет срабатывают при перечислении верхнего уровня,
  в том числе когда много исключаемых служебных имён.
- Не отправлены заголовки/байты при ошибке; известные ZIP-тесты сохранены.

### C09. Проверять открытие файлов на чтение до ответа ZIP — средний приоритет

**Места:** `Archive/FileSystemArchiveService.cs`: Plan/WriteAsync;
`Endpoints/ArchiveEndpoint.cs`, ArchivePlanTests/ArchiveEndpointTests.

**Дефект:** доступность метаданных не равна возможности открыть файл.
Заранее нечитаемый файл сейчас обнаруживается только во время записи ZIP.

**Изменение:** в предпроверке последовательно открывать обычный файл на чтение
с теми же существенными условиями доступа, что при записи, и сразу закрывать;
не читать содержимое и не держать дескрипторы всего дерева. Через общий
validator, после исправления C03. Появившиеся после предпроверки ошибки
по-прежнему обрывают ответ — снимок ФС/защита от локального злоумышленника
не обещаются.

**Готово, когда:**
- На Linux под не-root файл с доступными метаданными и запрещённым чтением
  приводит к 403/access_denied до начала ZIP (нет тела архива).
- Исчезновение/утрата прав после начала ответа обрывает соединение,
  не создаёт молча неполный «успешный» ZIP.
- После ошибки/успеха не растёт число открытых файлов, бюджет C08 соблюдён.

### C12. Атомарно создавать новую папку — низкий приоритет

**Места:** `FileSystem/FileSystemWriteService.cs`: CreateDirectory;
`FileSystemWriteTests.cs`.

**Дефект:** Exists + Directory.CreateDirectory может вернуть успех, когда
конкурент уже создал папку. Внутрипроцессный lock не закрывает эту гонку.

**Изменение:** операция создания ровно одного каталога, атомарно возвращающая
конфликт при существующем имени. При необходимости небольшой Windows/Linux
адаптер mkdir/CreateDirectory без recursive-create и без эвристик текста ошибок.
Сохранить resolver, ошибки доступа и no-overwrite. Не удалять конфликтующий
каталог «для отката», не использовать незарегистрированный временный мусор.

**Готово, когда:**
- Управляемая гонка: после предпроверки конкурент создаёт имя, операция
  возвращает name_conflict, конкурентный объект/содержимое сохранены.
- Среди двух одновременных mkdir одного имени ровно один успех; варианты
  уже существующего файла/папки/ссылки безопасны. Windows и Linux проверены.

### C15. Убрать N+1 и лишнее чтение истории на прогрессе

**Места:** `Tasks/TaskRepository.cs`: GetActiveAsync/GetHistoryPageAsync/GetPageAsync,
GetSources/GetItems; `Components/Tasks/TaskPanel.razor`.

**Дефект:** на каждую задачу отдельно запрашиваются источники и элементы,
а каждое уведомление прогресса запускает повторное чтение страницы истории.

**Изменение:** пакетно читать items для выбранных task id и строить sources
из этих же данных, ограничив число запросов независимо от количества задач
страницы. Все параметры bind, без конкатенации значений SQL. Историю
перечитывать при завершении/очистке/переходе страницы/ручном refresh/reconnect,
а не при каждом изменении байтов активной задачи. При отсутствии достаточно
точного вида уведомлений добавить минимальную классификацию; не терять финал.
Не вводить новый кэш как источник истины и не создавать ORM.

**Готово, когда:**
- На странице из 50 задач число SELECT для построения списка постоянно
  (например, основной запрос + пакет items), а не 1+2N; приведены замеры до/после.
- Серия progress-событий не перечитывает историю; завершение/ошибка/отмена
  сразу перемещают карточку и обновляют листинг. Последнее уведомление не теряется.
- Пагинация/очистка/reconnect, пустые страницы и все 4 типа задач проверены;
  sources/items/сортировка совпадают с прежним контрактом. Соединения не разделяются.

### C16. Заменить разбор текста SQLite-ошибок

**Готово, когда:** реальный UNIQUE-конфликт распознаётся, FK/иная ошибка
пробрасывается, обычное исключение со словом UNIQUE не считается коллизией;
в трёх местах нет эвристики по тексту. Файловая атомарная публикация сохранена.
