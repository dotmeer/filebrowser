# Self-hosted веб-файлменеджер

Статус документа: спецификация MVP для реализации.

## 1. Назначение

Docker-приложение для просмотра и управления файлами через браузер.

Приложение работает только с каталогами, перечисленными в конфигурации.
Каждый каталог отображается отдельным корнем.

Основной сценарий: один владелец или небольшая группа пользователей
в доверенной домашней сети.

## 2. Источники истины

- `docs/SPEC.md` — требования, границы MVP, итерации и промпты.
- `AGENTS.md` — постоянные правила разработки.
- `docs/PROJECT_STATE.md` — фактическое состояние и передача между сессиями.
- исходный код и тесты — реализованное поведение.

После начала разработки источником истины является репозиторий.
Внешние копии документации не должны независимо изменяться.

Изменения требований фиксируются в этом документе и в разделе решений
`docs/PROJECT_STATE.md`.

Статус задачи не считается подтверждением её работоспособности:
в PROJECT_STATE отдельно записываются выполненные проверки.

## 3. Границы MVP

### Входит

- несколько корней файловой системы;
- дерево каталогов;
- список содержимого каталога;
- навигация через URL;
- мультивыбор;
- создание папки;
- переименование;
- безвозвратное удаление одного объекта;
- скачивание одного файла;
- фоновое копирование и перемещение;
- очередь с ограниченной параллельностью;
- прогресс и скорость задач;
- история задач в SQLite;
- Docker;
- логи, базовые метрики и трассировка;
- автоматические тесты критичной логики.

### Не входит

- авторизация, пользователи и роли;
- предпросмотр;
- редактор файлов;
- поиск;
- корзина;
- отмена и приостановка задач;
- повторный запуск неудачных или прерванных задач;
- продолжение задач после перезапуска;
- загрузка файлов на сервер;
- скачивание папок и нескольких объектов (ZIP);
- массовое удаление;
- распаковка архивов;
- редактирование config.yaml через UI;
- настройка ACL и владельца файлов;
- сохранение всех файловых метаданных;
- работа с symlink;
- мобильный интерфейс как отдельная цель;
- отдельный публичный SignalR Hub;
- кластерный запуск нескольких экземпляров приложения.

## 4. Технологии

- .NET 10 LTS;
- ASP.NET Core;
- Blazor Web App, Interactive Server;
- Minimal API для HTTP-операций;
- SQLite через Microsoft.Data.Sqlite, без EF Core;
- YAML через YamlDotNet;
- xUnit;
- стандартные xUnit assertions;
- дополнительные тестовые библиотеки — только при необходимости;
- OpenTelemetry.

Версии зависимостей фиксируются в файлах проекта.
SDK фиксируется через global.json с явно выбранной политикой roll-forward.

Один серверный проект и один тестовый проект.
Без микросервисов, CQRS и дополнительных архитектурных фреймворков.

## 5. Развёртывание

### 5.1. Docker

- Linux-контейнер;
- multi-stage Dockerfile;
- внутренний порт 8080;
- непривилегированный пользователь;
- совместимость с запуском от заданного UID/GID;
- без privileged mode;
- без Docker socket;
- только необходимые mounts.

Пример Compose по умолчанию публикует:
`127.0.0.1:8080:8080`.

Для доступа из LAN пользователь явно меняет binding и отвечает
за сетевые ограничения.

### 5.2. Хранение

- `/config/config.yaml` — конфигурация;
- `/config/app.db` — SQLite;
- `/config` — постоянный writable volume;
- корни данных — отдельные mounts.

SQLite должен находиться на локальной файловой системе хоста.
Размещение app.db на SMB/NFS не поддерживается.

Приложение запускается в одном экземпляре на одну app.db.

### 5.3. Health check

`GET /healthz`

- 200: приложение готово обслуживать запросы;
- 503: приложение ещё не готово или обнаружена критичная неисправность.

Проверка не выполняет запись в корни данных.
Тело ответа не раскрывает физические пути.

## 6. Конфигурация

```yaml
workers: 2

roots:
  - name: temp
    path: /srv/temp
  - name: media
    path: /data/media
```

### 6.1. Правила

- конфигурация читается один раз при старте;
- hot reload отсутствует;
- workers: целое число от 1 до 16, по умолчанию 2;
- минимум один корень;
- name: `[a-z0-9][a-z0-9_-]{0,63}`;
- name одновременно является стабильным публичным идентификатором корня;
- имена уникальны без учёта регистра;
- path — абсолютный путь внутри контейнера;
- symlink в пути настроенного корня не допускается;
- одинаковые и вложенные физические корни не допускаются;
- пересечение корней с `/config` не допускается.

При изменении name старые URL могут перестать работать.
Это допустимо и должно быть описано в README.

### 6.2. Ошибки старта

Запуск завершается с понятной ошибкой при:

- отсутствующем или невалидном config.yaml;
- неизвестных полях конфигурации;
- невалидных значениях;
- дубликатах;
- пересечении корней;
- невозможности открыть или инициализировать SQLite.

Недоступность корня не останавливает запуск: см. 6.3.

Путь к YAML задаётся настройкой `ConfigPath` стандартной конфигурации
ASP.NET Core, по умолчанию `/config/config.yaml`.

Путь к SQLite — `/config/app.db`.
Для тестов допускается подмена через конфигурацию тестового хоста.

### 6.3. Доступность корней

Корень считается недоступным, если:

- путь отсутствует;
- недостаточно прав доступа;
- файловая система временно недоступна;
- путь является файлом, а не каталогом;
- в пути корня есть symlink.

Недоступный корень не останавливает запуск приложения.
Он отображается в UI как недоступный, остальные корни продолжают работать.
Состояние проверяется заново при каждом обращении или обновлении и не
считается постоянным: после восстановления доступа корень можно открыть
без перезапуска приложения.

Подробная причина записывается в серверный лог.
Клиенту раскрывается только обобщённая причина.

## 7. Адресация файлов

Физические серверные пути не передаются клиенту.

Все публичные ссылки на объекты имеют вид:

```json
{
  "root": "media",
  "path": "movies/example.mkv"
}
```

- root — name из конфигурации;
- path — относительный путь внутри корня;
- пустой path обозначает корень;
- разделитель в публичном контракте — `/`;
- абсолютные пути запрещены;
- сегменты `.` и `..` запрещены;
- обратный слеш запрещён;
- NUL и некорректное кодирование запрещены;
- URL декодируется стандартным HTTP-слоем, без повторного декодирования.

Новые имена проверяются отдельно:

- одно имя, не путь;
- не пустое;
- не `.` и не `..`;
- без `/`, `\` и NUL;
- без зарезервированного префикса `.filebrowser-`.

Регистр существующих файлов определяется файловой системой.
Приложение не приводит файловые имена к нижнему регистру.

## 8. Безопасность файловой системы

Все операции используют единый компонент разрешения и проверки пути.

Проверяется:

1. существование root;
2. корректность относительного пути;
3. нормализованный физический путь;
4. принадлежность корню по границе сегмента, а не простому StartsWith;
5. отсутствие symlink во всех существующих компонентах пути;
6. для создания объекта — безопасность родителя и нового имени.

Проверки выполняются и при приёме запроса, и при исполнении фоновой задачи.

### 8.1. Symlink и специальные файлы

В MVP:

- ссылки можно показать как неподдерживаемые элементы;
- переход по ссылке запрещён;
- скачивание, загрузка поверх, переименование и удаление ссылки запрещены;
- рекурсивные операции не следуют по ссылкам;
- обнаружение ссылки при предварительном обходе завершает операцию ошибкой;
- другие специальные объекты, например FIFO и socket, не обрабатываются.

Поддерживаются обычные файлы и каталоги.

### 8.2. Ограничения защиты

Приложение рассчитано на доверенный хост.

Не гарантируется защита от злонамеренного локального процесса, меняющего
компоненты пути между проверкой и открытием объекта.

Docker mounts и права ОС являются дополнительной границей доступа.
Запрещено описывать строковую проверку пути как полноценную песочницу.

### 8.3. Корни

Корень можно:

- просматривать;
- выбирать как целевую папку.

Сам корень нельзя:

- удалять;
- переименовывать;
- копировать как исходный объект;
- перемещать;
- скачивать (скачивание папок в MVP не поддерживается).

### 8.4. Сеть

Приложение без авторизации предназначено только для доверенной сети.

Необходимо:

- не включать permissive CORS;
- защищать изменяющие HTTP-запросы antiforgery-механизмом;
- не выполнять изменения через GET;
- не раскрывать stack trace и физические пути в API-ошибках;
- разрешить стандартную middleware-интеграцию авторизации в будущем.

Таблицы пользователей заранее не создаются.

## 9. Пользовательский интерфейс

### 9.1. Экран

- слева дерево каталогов;
- справа таблица текущей папки;
- сверху breadcrumbs, действия, задачи и меню настроек;
- дерево загружается лениво, без полного обхода всех корней;
- интерфейс на русском языке.

### 9.2. Таблица

Колонки:

- checkbox;
- имя;
- тип;
- размер файла;
- время изменения.

Размер каталога в списке не вычисляется рекурсивно: для каталогов
отображается `—`, размер показывается только для файлов.

Каталоги показываются раньше файлов, затем сортировка по имени
(ordinal-сравнение, фиксированная, без переключения по столбцам).

Скрытые объекты (имя с ведущей точкой) показываются и доступны
для операций, как и обычные. Исключение — служебные объекты приложения
с префиксом `.filebrowser-`: они не отображаются.

Длинные имена визуально обрезаются; полное имя показывается в tooltip.
Имя файла показывается целиком, включая расширение.

Даты передаются как `modifiedAtUtc` и отображаются в локальном
часовом поясе браузера.

Мультивыбор — checkbox.
Ctrl+клик, Shift+клик и сложная клавиатурная навигация не обязательны в MVP.

### 9.3. URL

```text
/browse?root=media&path=movies
```

- поддерживаются прямые ссылки;
- работают назад/вперёд;
- при отсутствии root открывается первый настроенный корень;
- при ошибочном URL показывается ошибка с возможностью вернуться к корню.

### 9.4. Действия

- создать папку — для текущей папки;
- переименовать — один объект;
- удалить — ровно один объект;
- копировать/переместить — один или несколько, с выбором целевой папки;
- скачать — ровно один файл;
- обновить — перечитать текущую папку.

Создание папки не зависит от наличия выделения.

Удаление доступно только при выборе ровно одного объекта.
Скачивание доступно только при выборе ровно одного файла;
при выборе папки или нескольких объектов кнопка недоступна.

После операции текущий интерфейс обновляется.
Изменения внешними процессами появляются после ручного обновления
или повторного открытия папки.
FileSystemWatcher не используется в MVP.

### 9.5. Удаление

Безвозвратное, для каталогов рекурсивное.

Массовое удаление не поддерживается: за один запрос удаляется
ровно один объект.

Модальное окно содержит:

- удаляемый объект;
- предупреждение;
- checkbox подтверждения;
- заблокированную до установки checkbox кнопку удаления.

Удаление выполняется HTTP-запросом, не фоновой задачей.
Для больших деревьев может занимать длительное время.
Возобновление удаления после обрыва запроса не гарантируется.

### 9.6. Состояния

- загрузка;
- пустая папка;
- нет доступа;
- объект исчез;
- ошибка операции;
- потеря подключения к серверу;
- недоступное действие;
- неопределённый прогресс.

Настройки — страница-заглушка с пояснением о config.yaml.

## 10. Политика файловых операций

### 10.1. Конфликты имён

Единая политика для всех операций: **конфликт имени всегда ошибка,
автоматическое переименование не выполняется.**

- создание папки: существующее имя → 409;
- переименование: существующее имя → 409;
- copy/move: конфликт итогового имени в назначении → ошибка задачи
  `name_conflict`;
- существующие объекты никогда не перезаписываются;
- каталоги не объединяются;
- суффиксы вида `(1)`, `(2)` не подбираются;
- пользователь сам устраняет конфликт (переименует объект, выберет
  другое имя или другую целевую папку).

Проверка Exists сама по себе недостаточна: она не защищает от
конкурентной публикации. Окончательная публикация не должна заменять
существующий объект.

Конкурентные задачи заранее не блокируются. Первая задача, успешно
опубликовавшая объект, выигрывает; остальные получают ошибку
`name_conflict`. Результат определяется фактическим порядком выполнения.

Граница регистра определяется фактическим поведением файловой системы:
приложение не вводит собственную нормализацию регистра.

### 10.2. Источники и назначения

Все выбранные источники должны находиться в одной родительской папке.
При UI-выборе это гарантировано ограничением на один уровень; сервер
не полагается на UI и отклоняет запрос с источниками из разных папок (400).

Запрещены:

- источник и назначение, обозначающие один объект;
- копирование/перемещение в ту же родительскую папку;
- перенос каталога внутрь самого себя;
- перенос каталога в собственного потомка;
- исходный список, одновременно содержащий каталог и его потомка;
- изменение корня;
- операция с неподдерживаемым объектом.

Целевой папкой может быть любой разрешённый каталог, включая каталог
другого корня. Запрещено выбирать в качестве цели:

- текущую папку;
- выбранный исходный каталог;
- потомка выбранного исходного каталога.

Родительская папка выбранного файла допустима как целевая.

Копирование и перемещение между любыми корнями разрешены.

Точные дубликаты выбранных источников удаляются до исполнения.

Порядок обработки источников: сервер сортирует их по полному
публичному пути с ordinal-сравнением строк. Порядок выбора в UI
не учитывается.

### 10.3. Изменение данных сторонними процессами

Снимок файловой системы не создаётся.

Если источник изменился или исчез, операция может завершиться ошибкой.
Приложение не обещает консистентную резервную копию активно изменяемых данных.

### 10.4. Частичный результат

Операции над несколькими объектами не являются общей транзакцией.

При ошибке:

- уже завершённые объекты не откатываются;
- существующие чужие данные не изменяются;
- результат содержит выполненные и неудачные элементы;
- пользователь явно видит частичное выполнение.

### 10.5. Двухфазная модель copy/move

Операции над несколькими объектами не являются общей транзакцией.

1. **Предварительная проверка** (этап `scanning`):
   - проверяются источники, целевой каталог, конфликты имён, symlink,
     неподдерживаемые объекты и вложенность;
   - собираются **все** найденные ошибки;
   - при наличии хоть одной ошибки операция не начинается;
   - задача получает `failed` и показывает сгруппированный список ошибок
     по объектам.

2. **Выполнение**: идёт по отсортированному списку источников
   и останавливается на первой фактической ошибке:
   - текущий объект получает ошибку;
   - последующие верхнеуровневые объекты помечаются как необработанные;
   - уже завершённые объекты сохраняются;
   - задача получает `failed` с указанием ошибочного объекта.

Порядок обработки не зависит от конкурентных задач; конфликты
определяются фактическим порядком публикации (см. 10.1).

Удаление выполняется только для одного объекта за раз.

## 11. Загрузка файлов — не входит в MVP

Загрузка файлов на сервер в MVP не реализуется.

Все связанные аспекты — API, множественная загрузка, лимиты размера,
прогресс, временные файлы, защита от перезаписи, обработка обрыва
соединения, drag-and-drop, загрузка папок — отложены в roadmap.
Перед началом этой работы они проектируются отдельно; решения,
обсуждавшиеся ранее, обязательными не считаются.

## 12. Download

### 12.1. Один файл

- обычный HTTP stream;
- корректный Content-Disposition;
- application/octet-stream;
- без открытия пользовательского HTML/SVG inline;
- Content-Length, если известен;
- поддержка Range через стандартные возможности ASP.NET Core.

### 12.2. Папки и наборы объектов — не входит в MVP

Скачивание папки и нескольких объектов (ZIP) в MVP не реализуется
и отложено в roadmap: потоковая генерация ZIP, сохранение относительной
структуры, пустые папки, защита записей архива, поведение при ошибке
после начала ответа.

В MVP скачивается только один обычный файл.

## 13. Copy и move

### 13.1. Очередь

- BackgroundService;
- bounded Channel;
- ёмкость ожидающей очереди — 100;
- число workers из config.yaml;
- при заполнении — 429 с понятной ошибкой;
- SQLite хранит авторитетное состояние;
- Channel содержит идентификаторы задач, а не единственную копию данных.

Очерёдность выполнения — FIFO: задачи запускаются в порядке постановки
(`created_at`, при совпадении — `id`). Приоритетов нет; размер, тип
и источник задачи на порядок не влияют.

Сначала задача сохраняется, затем допускается к выполнению.
Ошибка помещения в очередь не должна оставлять вечную queued-задачу.

### 13.2. Состояния

- queued;
- scanning;
- running;
- completed;
- failed;
- interrupted.

`scanning` — предварительный обход и оценка объёма.

При старте queued/scanning/running переводятся в interrupted.
Автоматическое продолжение и повторное исполнение отсутствуют.

### 13.3. Copy

Для каждого верхнеуровневого источника:

1. проверить источник и целевой каталог;
2. создать уникальный временный объект на стороне назначения;
3. скопировать содержимое;
4. закрыть файловые дескрипторы;
5. опубликовать под конечным именем без перезаписи.

Финальное имя появляется только после успешного копирования объекта.
При конфликте имени задача получает ошибку `name_conflict`; суффиксы
не подбираются (см. 10.1).

### 13.4. Move

- сначала попробовать атомарное файловое переименование, если возможно;
- при переносе между файловыми системами использовать copy + delete;
- fallback разрешён при подтверждённой ошибке cross-device,
  а не при любом IOException;
- источник удаляется только после успешного копирования и публикации;
- если удаление источника не удалось, задача failed;
- результат явно сообщает, что назначение создано, а источник мог сохраниться
  полностью или частично;
- автоматический откат назначения не выполняется.

Перед реализацией fallback необходимо подтвердить способ определения
cross-device ошибки для выбранной Linux/.NET-среды тестом.
Если переносимого managed API недостаточно, допускается небольшой
изолированный Linux-адаптер вместо эвристики по тексту исключения.

### 13.5. Временные объекты

Префикс: `.filebrowser-`.

Они:

- скрываются из обычного листинга;
- недоступны через публичные файловые операции;
- не создаются пользователем через API;
- регистрируются в SQLite до создания на диске.

После перезапуска приложение может удалять только точно зарегистрированные
собственные временные объекты, повторно проверив путь.

Удалять все файлы по маске `.filebrowser-*` запрещено.

### 13.6. Прогресс

- для каталогов предусмотрены этапы:
  - `scanning` — «Проверка и подсчёт»: процент не показывается;
  - `running` — копирование/перемещение: процент, обработанные байты,
    скорость относительно предварительной оценки;
  - `completed` / `failed` / `interrupted`;
- во время scanning процент неизвестен;
- после сканирования известны оценочные bytes_total и items_total;
- bytes_done растёт по фактически скопированным байтам;
- скорость — скользящее окно 5 секунд;
- обновления UI — не чаще 2 раз в секунду на задачу;
- запись промежуточного прогресса в SQLite — не чаще раза в секунду;
  переходы состояния и финальный результат сохраняются сразу;
- после переподключения или потери уведомления состояние полностью
  перечитывается из SQLite;
- во время удаления источника move может оставаться на 100%,
  но не считается completed до завершения удаления;
- пустые деревья отображаются корректно без деления на ноль;
- при изменении источника оценка может перестать быть точной;
- переименование внутри файловой системы может завершиться сразу:
  задача считается completed после успешного атомарного rename,
  длительного прогресса и «искусственной» скорости нет.

### 13.7. История

Сохраняются:

- id;
- тип;
- список источников;
- назначение;
- состояние;
- текущий этап;
- bytes_done/bytes_total;
- items_done/items_total;
- безопасное описание ошибки;
- время создания, старта, обновления и завершения.

Результат хранится агрегированно по верхнеуровневым выбранным объектам:
для каждого — статус (обработан / ошибка / не обработан), для каталога —
счётчики обработанного и найденного, ошибочный путь и причина.
Детальные записи по каждому вложенному файлу не создаются.

Скорость допустимо хранить только в памяти.
При отсутствии активного выполнения отображается 0.

Панель показывает последние 50 задач с пагинацией; отдельной страницы
истории нет. Активные задачи всегда доступны.

Кнопка «Очистить историю» удаляет **все неактивные** задачи
(`completed`, `failed`, `interrupted`) вместе с их результатом, в рамках
одной транзакции. Файлы при этом не изменяются. Удаляются только задачи,
неактивные на момент начала транзакции: если задача стала активной
одновременно с очисткой, она не удаляется.
Автоматического ограничения срока или количества записей нет.

## 14. SQLite

- Microsoft.Data.Sqlite;
- параметризованные запросы;
- короткие транзакции;
- foreign keys включены;
- настроен busy timeout;
- изменения схемы через нумерованные миграции;
- выполненные миграции учитываются в БД;
- схема обновляется идемпотентно;
- соединения не разделяются небезопасно между потоками;
- одна операция файлового копирования не держит транзакцию БД открытой.

Минимальные сущности:

- schema_migrations;
- tasks;
- task_items;
- temporary_artifacts.

Детальная SQL-схема определяется в итерации хранения,
но должна поддерживать контракты этого документа.

Повреждённая или недоступная база останавливает запуск. Автоматическое
восстановление (`integrity_check`, переименование, пересоздание) не
выполняется: пользователь сам решает, как восстановить базу.

Автоматические резервные копии базы не создаются. README описывает
необходимость резервировать `/config` (app.db и config.yaml) средствами
владельца. Backup базы не должен выполняться поверх работающего приложения.

## 15. Обновления задач в Blazor

Отдельный TasksHub не создаётся.

- серверный сервис публикует уведомления об изменении задач;
- компонент подписывается на время жизни;
- обновляет UI через InvokeAsync;
- корректно отписывается;
- при новом подключении и переподключении полностью перечитывает
  актуальное состояние из SQLite;
- потерянное уведомление не приводит к потере задачи;
- можно выполнить ручное обновление списка.

Blazor-компоненты вызывают прикладные сервисы напрямую.
Не нужно заставлять серверный компонент вызывать собственное HTTP API.

HTTP API использует те же прикладные сервисы, без дублирования правил.

## 16. HTTP API

Общие DTO используют root + относительный path.
Физические пути в ответах отсутствуют.

### Чтение

- GET `/api/fs/roots`
- GET `/api/fs/list?root=...&path=...`

Корни содержат публичное имя, но не физический path.

Элемент списка:

- name;
- path;
- kind: file/directory/unsupported;
- size: nullable;
- modifiedAtUtc.

### Изменения

- POST `/api/fs/mkdir`
  - parent: FileRef;
  - name.

- POST `/api/fs/rename`
  - source: FileRef;
  - newName.

- POST `/api/fs/delete`
  - source: FileRef — ровно один объект.

### Передача

- GET `/api/fs/download?root=...&path=...`
  - только один обычный файл;
  - поддержка Range;
  - корректный Content-Disposition;
  - `application/octet-stream`.

### Задачи

- POST `/api/tasks/copy`
  - sources: FileRef[];
  - destination: FileRef.

- POST `/api/tasks/move`
  - тот же контракт.

- GET `/api/tasks?offset=0&limit=50`
  - limit не более 100.

- GET `/api/tasks/{id}`

- DELETE `/api/tasks/history`
  - очистить историю: удалить все неактивные задачи
    (`completed`, `failed`, `interrupted`);
  - активные задачи не удаляются;
  - подтверждение через antiforgery;
  - файлы не изменяются.

Создание задачи возвращает 202, id и Location.
Простые успешные операции возвращают фактический результат.

## 17. Ошибки

Использовать ASP.NET Core ProblemDetails:

- type;
- title;
- status;
- detail;
- code — стабильный машинный код;
- traceId.

Не раскрывать stack trace и физические пути.

Статусы:

- 400 — невалидный запрос или запрещённый публичный путь;
- 403 — нет прав ОС;
- 404 — объект не найден;
- 409 — конфликт имени (`name_conflict`);
- 429 — очередь заполнена;
- 500 — непредвиденная ошибка.

Для операции с частью ошибок внутри самой операции (например, задача
copy/move, остановленная на первой ошибке) применяется контракт задачи:
задача получает `failed`, результат содержит ошибочный объект
и необработанные объекты. Это не означает, что все объекты обработаны.

## 18. Наблюдаемость

Обязательно:

- структурированные console logs;
- traceId в ошибках;
- идентификатор задачи в логах задачи;
- логи старта, конфигурационных ошибок, задач и файловых ошибок;
- базовая ASP.NET Core tracing-инструментация;
- spans copy/move;
- метрики количества активных и ожидающих задач, завершений и ошибок;
- опциональный OTLP exporter через стандартные OTEL_* переменные.

Без настроенного exporter приложение продолжает работать.
Полный observability stack не является зависимостью основного Compose.

Все настройки экспорта — стандартные переменные `OTEL_*`
(например, `OTEL_EXPORTER_OTLP_ENDPOINT`). Документация содержит
инструкцию подключения приложения к внешнему OTel Collector, уже
развёрнутому отдельно, включая настройку endpoint, заголовков
авторизации и resource-атрибутов.

Содержимое файлов не логируется.
Пути файлов не используются как labels метрик.

## 24. Критерии готовности MVP

- все обязательные функции реализованы;
- приложение запускается в Linux Docker не от root;
- конфигурация валидируется;
- недоступный корень не останавливает запуск приложения;
- наружу не раскрываются физические пути;
- путь и symlink проверяются во всех операциях;
- нет перезаписи существующих данных; конфликт имени → 409/name_conflict;
- copy/move имеют определённую семантику частичных ошибок;
- download идёт обычным HTTP;
- задачи сохраняются, очередь FIFO, после рестарта помечаются interrupted;
- очистка истории удаляет только неактивные задачи;
- изменяющие HTTP-запросы защищены antiforgery;
- тесты проходят;
- выполнена Linux-проверка;
- выполнен контейнерный smoke test;
- ограничения описаны;
- PROJECT_STATE соответствует фактическому состоянию.
