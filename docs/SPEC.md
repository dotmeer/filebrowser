# Self-hosted веб-файлменеджер

Статус документа: спецификация действующего продукта. MVP реализован;
изменения документа описывают доработку и сопровождение существующего
приложения.

## 1. Назначение

Docker-приложение для просмотра и управления файлами через браузер.

Приложение работает только с каталогами, перечисленными в конфигурации.
Каждый каталог отображается отдельным корнем.

Основной сценарий: один владелец или небольшая группа пользователей
в доверенной домашней сети.

## 2. Источники истины

- `docs/SPEC.md` — требования и границы MVP.
- `AGENTS.md` — постоянные правила разработки.
- `docs/PROJECT_STATE.md` — фактическое состояние и передача между сессиями.
- исходный код и тесты — реализованное поведение.

После начала разработки источником истины является репозиторий.
Внешние копии документации не должны независимо изменяться.

Изменения требований фиксируются в этом документе и в разделе решений
`docs/PROJECT_STATE.md`.

Статус задачи не считается подтверждением её работоспособности:
в PROJECT_STATE отдельно записываются выполненные проверки.

## 3. Границы MVP

### Входит

- несколько корней файловой системы;
- дерево каталогов;
- список содержимого каталога;
- навигация через URL;
- мультивыбор;
- создание папки;
- переименование;
- безвозвратное удаление одного или нескольких объектов фоновой задачей;
- скачивание одного файла;
- скачивание папки и набора объектов текущей папки одним ZIP-архивом;
- фоновое копирование и перемещение;
- очередь с ограниченной параллельностью;
- прогресс и скорость задач;
- история задач в SQLite;
- Docker;
- логи, базовые метрики и трассировка;
- автоматические тесты критичной логики.

### Не входит

- авторизация, пользователи и роли;
- предпросмотр видео и аудио — не планируется (решение D085);
- редактор файлов;
- корзина — не планируется (решение D086);
- повторный запуск неудачных или прерванных задач;
- продолжение задач после перезапуска;
- загрузка файлов на сервер;
- распаковка архивов;
- редактирование config.yaml через UI;
- настройка ACL и владельца файлов;
- сохранение всех файловых метаданных;
- работа с symlink;
- мобильный интерфейс как отдельная цель;
- отдельный публичный SignalR Hub;
- кластерный запуск нескольких экземпляров приложения.

## 4. Технологии

- .NET 10 LTS;
- ASP.NET Core;
- Blazor Web App, Interactive Server;
- Minimal API только для скачивания файла, скачивания архивом,
  предпросмотра файла и health-checks;
- SQLite через Microsoft.Data.Sqlite, без EF Core;
- YAML через YamlDotNet;
- xUnit;
- стандартные xUnit assertions;
- дополнительные тестовые библиотеки — только при необходимости;
- OpenTelemetry.

Версии зависимостей фиксируются в файлах проекта.
SDK фиксируется через global.json с явно выбранной политикой roll-forward.

Один серверный проект и один тестовый проект.
Без микросервисов, CQRS и дополнительных архитектурных фреймворков.

## 5. Развёртывание

### 5.1. Docker

- Linux-контейнер;
- multi-stage Dockerfile;
- внутренний порт 8080;
- непривилегированный пользователь;
- совместимость с запуском от заданного UID/GID;
- без privileged mode;
- без Docker socket;
- только необходимые mounts.

Пример Compose по умолчанию публикует:
`127.0.0.1:8080:8080`.

Для доступа из LAN пользователь явно меняет binding и отвечает
за сетевые ограничения.

### 5.2. Хранение

- `/config/config.yaml` — конфигурация;
- `/config/app.db` — SQLite;
- `/config` — постоянный writable volume;
- корни данных — отдельные mounts.

SQLite должен находиться на локальной файловой системе хоста.
Размещение app.db на SMB/NFS не поддерживается.

Приложение запускается в одном экземпляре на одну app.db.

### 5.3. Health check

Стандартный ASP.NET Core Health Checks middleware:

- `GET /health/live` — liveness: приложение отвечает;
- `GET /health/ready` — readiness: приложение готово обслуживать запросы.

В MVP зарегистрированных проверок нет: оба маршрута возвращают `200`,
как только приложение отвечает. При появлении критичной зависимости
(например, SQLite) в readiness добавляется соответствующая проверка,
и маршрут начинает возвращать `503` при её неудаче — это сценарий
запуска под оркестратором (k8s livenessProbe/readinessProbe).

Проверка не выполняет запись в корни данных.
Тело ответа не раскрывает физические пути.

## 6. Конфигурация

```yaml
workers: 2

roots:
  - name: temp
    path: /srv/temp
  - name: media
    path: /data/media
```

### 6.1. Правила

- конфигурация читается один раз при старте;
- hot reload отсутствует;
- workers: целое число от 1 до 16, по умолчанию 2;
- минимум один корень;
- name: `[a-z0-9][a-z0-9_-]{0,63}`;
- name одновременно является стабильным публичным идентификатором корня;
- имена уникальны без учёта регистра;
- path — абсолютный путь внутри контейнера;
- symlink в пути настроенного корня не допускается;
- одинаковые и вложенные физические корни не допускаются;
- корень может пересекаться с `/config`, каталогом SQLite или корневым
  каталогом файловой системы; служебные файлы, попавшие в корень,
  отображаются и обрабатываются как обычные объекты на страх и риск
  владельца.

При изменении name старые URL могут перестать работать.
Это допустимо и должно быть описано в README.

### 6.2. Ошибки старта

Запуск завершается с понятной ошибкой при:

- отсутствующем или невалидном config.yaml;
- неизвестных полях конфигурации;
- невалидных значениях;
- дубликатах;
- пересечении корней друг с другом;
- невозможности открыть или инициализировать SQLite.

Недоступность корня не останавливает запуск: см. 6.3.

Путь к YAML задаётся настройкой `ConfigPath` стандартной конфигурации
ASP.NET Core, по умолчанию `/config/config.yaml`.

Путь к SQLite определяется стандартной настройкой ASP.NET Core `DatabasePath`.
Если она не задана, используется `app.db` рядом с активным `ConfigPath`
(для стандартной конфигурации — `/config/app.db`). Для тестов допускается
подмена через конфигурацию тестового хоста.

`DatabasePath` допускается внутри настроенного корня. Приложение не скрывает
и не защищает `config.yaml` или `app.db`, попавшие в корень; их изменение,
переименование или удаление может нарушить работу приложения.

### 6.3. Доступность корней

Корень считается недоступным, если:

- путь отсутствует;
- недостаточно прав доступа;
- файловая система временно недоступна;
- путь является файлом, а не каталогом;
- в пути корня есть symlink.

Недоступный корень не останавливает запуск приложения.
Он отображается в UI как недоступный, остальные корни продолжают работать.
Состояние проверяется заново при каждом обращении или обновлении и не
считается постоянным: после восстановления доступа корень можно открыть
без перезапуска приложения.

Корень может совпадать с корневым каталогом файловой системы. Приложение
стартует, если сам путь доступен, но не создаёт вокруг такого корня
служебную изоляцию: все видимые объекты обрабатываются по общим правилам,
а последствия операций с системными и служебными файлами лежат на владельце.

Подробная причина записывается в серверный лог.
Клиенту раскрывается только обобщённая причина.

## 7. Адресация файлов

Физические серверные пути не передаются клиенту.

Все публичные ссылки на объекты имеют вид:

```json
{
  "root": "media",
  "path": "movies/example.mkv"
}
```

- root — name из конфигурации;
- path — относительный путь внутри корня;
- пустой path обозначает корень;
- разделитель в публичном контракте — `/`;
- абсолютные пути запрещены;
- сегменты `.` и `..` запрещены;
- обратный слеш запрещён;
- NUL и некорректное кодирование запрещены;
- URL декодируется стандартным HTTP-слоем, без повторного декодирования.

Новые имена проверяются отдельно:

- одно имя, не путь;
- не пустое;
- не `.` и не `..`;
- без `/`, `\` и NUL;
- без зарезервированного префикса `.filebrowser-`.

Регистр существующих файлов определяется файловой системой.
Приложение не приводит файловые имена к нижнему регистру.

### 7.1. Виртуальный корень

Приложение предоставляет дополнительный виртуальный корень
`AllRoots`, объединяющий все настроенные корни.

- имя `AllRoots` зарезервировано: оно не может быть задано
  в `config.yaml`, так как выходит за пределы допустимого алфавита
  имён корней (§6.1); правила конфигурации не меняются;
- пути внутри виртуального корня имеют вид
  `<имя реального корня>/<относительный путь>`; например,
  `AllRoots/media/movies` обозначает тот же объект, что
  `media/movies` реального корня;
- виртуальный корень доступен только для чтения: list, search
  и download. Все изменяющие операции (mkdir, rename, delete,
  copy/move) с `root=AllRoots` отклоняются с `400/invalid_request`;
- на верхнем уровне виртуального корня (`path` пуст) отображаются
  настроенные корни как каталоги; недоступный реальный корень
  показывается как недоступный элемент;
- чтение под виртуальным корнем выполняется делегированием
  существующим механизмам реальных корней; единый resolver/validator
  реальных корней не изменяется.

## 8. Безопасность файловой системы

Все операции используют единый компонент разрешения и проверки пути.

Проверяется:

1. существование root;
2. корректность относительного пути;
3. нормализованный физический путь;
4. принадлежность корню по границе сегмента, а не простому StartsWith;
5. отсутствие symlink во всех существующих компонентах пути;
6. для создания объекта — безопасность родителя и нового имени.

Проверки выполняются и при приёме запроса, и при исполнении фоновой задачи.

### 8.1. Symlink и специальные файлы

В MVP:

- ссылки можно показать как неподдерживаемые элементы;
- переход по ссылке запрещён;
- скачивание, загрузка поверх, переименование и удаление ссылки запрещены;
- рекурсивные операции не следуют по ссылкам;
- обнаружение ссылки при предварительном обходе завершает операцию ошибкой;
- другие специальные объекты, например FIFO и socket, не обрабатываются.

Поддерживаются обычные файлы и каталоги.

### 8.2. Ограничения защиты

Приложение рассчитано на доверенный хост.

Не гарантируется защита от злонамеренного локального процесса, меняющего
компоненты пути между проверкой и открытием объекта.

Если корень включает служебные файлы приложения, они не получают
дополнительной защиты: файловые операции с ними разрешены на уровне прав ОС.
Docker mounts и права ОС являются дополнительной границей доступа.
Запрещено описывать строковую проверку пути как полноценную песочницу.

### 8.3. Корни

Корень можно:

- просматривать;
- выбирать как целевую папку.

Сам корень нельзя:

- удалять;
- переименовывать;
- копировать как исходный объект;
- перемещать;
- скачивать (скачивание папок в MVP не поддерживается).

### 8.4. Сеть

Приложение без авторизации предназначено только для доверенной сети.

Необходимо:

- не включать permissive CORS;
- не выполнять изменения через GET;
- не раскрывать stack trace и физические пути в ошибках HTTP-эндпоинтов;
- разрешить стандартную middleware-интеграцию авторизации в будущем.

Внешний изменяющий HTTP API не предоставляется (решение «Удаление
внешнего HTTP API»): все изменения выполняются через Blazor, который
вызывает прикладные сервисы напрямую, вне HTTP-пайплайна. Антиподделочная
защита antiforgery сохраняется как часть инфраструктуры Blazor Web App,
но наружу не торчит: изменяющих эндпоинтов нет.

Таблицы пользователей заранее не создаются.

## 9. Пользовательский интерфейс

### 9.1. Экран

- слева дерево каталогов, справа таблица текущей папки, справа от таблицы
  панель задач;
- дерево, таблица и панель задач разделены перетаскиваемыми разделителями;
  каждая панель имеет минимальную ширину, ограничивающую сжатие;
- сверху строка заголовка: название приложения слева и меню приложения
  (кнопка «бургер») справа; в меню — «Настройки»;
- на странице «Настройки» — выбор темы оформления и кнопка возврата
  на предыдущую страницу;
- над таблицей — breadcrumbs и панель действий;
- дерево загружается лениво, без полного обхода всех корней;
- дерево каталогов имеет единственный узел верхнего уровня —
  виртуальный корень «Все корни» (см. §7.1); настроенные корни
  отображаются только как его дочерние элементы и не дублируются
  на верхнем уровне; внутри виртуального корня изменяющие действия
  недоступны (кнопки заблокированы), чтение и скачивание доступны;
- интерфейс локализован: английский язык по умолчанию и русский;
  язык выбирается в «Настройках» и хранится на сервере (SQLite),
  поэтому одинаков для всех браузеров и клиентов.

### 9.2. Таблица

Колонки:

- checkbox;
- имя;
- тип;
- размер файла;
- время изменения.

Размер каталога в списке не вычисляется рекурсивно: для каталогов
отображается `—`, размер показывается только для файлов.

Каталоги показываются раньше файлов, затем сортировка по имени
(ordinal-сравнение, фиксированная, без переключения по столбцам).

Скрытые объекты (имя с ведущей точкой) показываются и доступны
для операций, как и обычные. Исключение — служебные объекты приложения
с префиксом `.filebrowser-`: они не отображаются.

Длинные имена визуально обрезаются; полное имя показывается в tooltip.
Имя файла показывается целиком, включая расширение.

Даты передаются как `modifiedAtUtc` и отображаются в локальном
часовом поясе браузера.

Мультивыбор — checkbox.
Ctrl+клик, Shift+клик и сложная клавиатурная навигация не обязательны в MVP.

### 9.3. URL

```text
/?root=media&path=movies
```

- поддерживаются прямые ссылки;
- работают назад/вперёд;
- при отсутствии root открывается первый настроенный корень;
- при ошибочном URL показывается ошибка с возможностью вернуться к корню.

### 9.4. Действия

- создать папку — для текущей папки;
- переименовать — один объект;
- удалить — один или несколько объектов текущей папки фоновой задачей
  (§9.5, §13.9);
- копировать/переместить — один или несколько, с выбором целевой папки;
- скачать — ровно один файл; папку или набор объектов текущей папки —
  одним ZIP-архивом (§12.2);
- предпросмотр — ровно один файл типа изображение, PDF или текст
  (§16 «Предпросмотр»); открывается модальное окно по двойному клику
  по имени файла или из контекстного меню; доступен и в виртуальном
  корне (операция чтения);
- обновить — перечитать текущую папку.

Создание папки не зависит от наличия выделения.

Удаление доступно при любом непустом выделении в текущей папке;
результаты поиска и виртуальный корень удалять нельзя.
Скачивание файла доступно только при выборе ровно одного файла.
Скачивание архивом (§12.2) доступно при любом непустом выделении
и из контекстного меню каталога. В узле «Все корни» (список корней)
архив доступен для ровно одного выбранного корня: он скачивается
как `<корень>.zip`. Несколько корней сразу скачать нельзя — у них нет
общей родительской папки. Внутри реального корня, открытого через
«Все корни», архив доступен — путь делегируется реальному корню,
как при скачивании файла.

После операции текущий интерфейс обновляется.
Изменения внешними процессами появляются после ручного обновления
или повторного открытия папки.
FileSystemWatcher не используется в MVP.

### 9.5. Удаление

Безвозвратное, для каталогов рекурсивное. Выполняется фоновой задачей
(§13.9), поэтому доступны предпроверка, частичный результат, отмена
и запись в историю; отдельной синхронной операции удаления в UI нет.

Правила:

- удаляются только объекты текущей папки (одна родительская папка,
  §10.2); корень удалить нельзя;
- предпроверка собирает все ошибки и не начинает удаление при любой
  из них: symlink и специальные объекты внутри дерева, недоступные
  объекты, файлы с атрибутом `ReadOnly` (атрибут не снимается);
- запрещено удалять дерево, внутри которого находятся служебные файлы
  приложения (`config.yaml`, файл SQLite и его sidecar-файлы) или
  зарегистрированные временные артефакты задач;
- удаление атомарно по имени: объект переименовывается в
  зарегистрированный временный артефакт в той же папке, затем артефакт
  удаляется. После переименования имя сразу свободно;
- физическое освобождение места может завершиться позже: если процесс
  остановлен между переименованием и удалением артефакта, артефакт
  удаляется при следующем старте (§13.5);
- если артефакт удалить не удалось, объект получает ошибку
  `delete_incomplete`: данные скрыты из пространства имён, место
  освободится при следующем старте;
- отмена возможна только между верхнеуровневыми объектами; для
  каталога переименование и удаление артефакта не прерываются
  (§13.9);
- удаление не является общей транзакцией: частичный результат
  подчиняется §10.4;
- назначения активных задач не защищаются: удаление папки, в которую
  пишет задача, приводит к ошибке этой задачи.

Модальное окно содержит:

- удаляемый объект;
- предупреждение;
- checkbox подтверждения;
- заблокированную до установки checkbox кнопку удаления.

### 9.6. Состояния

- загрузка;
- пустая папка;
- нет доступа;
- объект исчез;
- ошибка операции;
- потеря подключения к серверу;
- недоступное действие;
- неопределённый прогресс.

Страница «Настройки» содержит:

- пояснение, что серверная конфигурация задаётся в `config.yaml`
  и применяется после перезапуска приложения;
- выбор языка интерфейса: английский (по умолчанию) или русский;
  выбор сохраняется на сервере в SQLite (таблица `app_settings`),
  общий для всех клиентов и применяется после полной перезагрузки
  страницы (не через enhanced navigation): культура Blazor circuit
  фиксируется при его создании;
- выбор темы оформления: системная, светлая или тёмная; выбор хранится
  в браузере (`localStorage`), не входит в `config.yaml` и применяется
  сразу; по умолчанию используется системная тема;
- кнопку возврата на предыдущую страницу; если предыдущей страницы
  приложения нет (прямое открытие `/settings`), выполняется переход
  на главную `/`.

Смена языка выполняется обработчиком Blazor на странице `/settings`:
значение сохраняется через `AppSettingsService.SetLanguageAsync` и
выполняется полная перезагрузка страницы, чтобы middleware локализации
применил новую культуру ко всей странице и будущим Blazor circuit.
Неподдерживаемое значение отклоняется `AppSettingsService` (исключение
`ArgumentException` до записи в SQLite).

Тема оформления задаётся на уровне клиента и не синхронизируется
между браузерами.

### 9.7. Поиск

- строка поиска находится в панели действий над таблицей;
- пока активен поиск, таблица текущей папки заменяется таблицей
  результатов с той же разметкой и сортировкой (§9.2);
- breadcrumbs в режиме поиска заменяются заголовком
  «Результаты поиска: «запрос»» и кнопкой выхода из поиска;
- клик по каталогу в результатах открывает его по пути результата;
  клик по файлу открывает родительскую папку с подсветкой найденного
  файла (имя передаётся query-параметром `highlight`);
- чекбоксы и операции над объектами в результатах не предоставляются:
  операции доступны после перехода к объекту штатными средствами
  (ограничение §10.2 на общего родителя для copy/move сохраняется);
- во время выполнения поиска показывается состояние «Поиск…»
  с неопределённым индикатором; файловый обход не выполняется
  синхронно на UI-потоке;
- под именем каждого объекта в результатах всегда показывается
  родительский путь от корня мелким приглушённым текстом, с префиксом
  `/` и включая имя корня (для виртуального корня — имя реального
  корня, пути результатов уже начинаются с него); длинный путь
  визуально обрезается по ширине ячейки; полный путь объекта от корня —
  во всплывающей подсказке (tooltip) ячейки и подзаголовка;
- строки интерфейса поиска локализуются (EN/RU) через ресурсы.

## 10. Политика файловых операций

### 10.1. Конфликты имён

Единая политика для всех операций: **конфликт имени всегда ошибка,
автоматическое переименование не выполняется.**

- создание папки: существующее имя → 409;
- переименование: существующее имя → 409;
- copy/move: конфликт итогового имени в назначении → ошибка задачи
  `name_conflict`;
- существующие объекты никогда не перезаписываются;
- каталоги не объединяются;
- суффиксы вида `(1)`, `(2)` не подбираются;
- пользователь сам устраняет конфликт (переименует объект, выберет
  другое имя или другую целевую папку).

Проверка Exists сама по себе недостаточна: она не защищает от
конкурентной публикации. Окончательная публикация не должна заменять
существующий объект.

Конкурентные задачи заранее не блокируются. Первая задача, успешно
опубликовавшая объект, выигрывает; остальные получают ошибку
`name_conflict`. Результат определяется фактическим порядком выполнения.

Граница регистра определяется фактическим поведением файловой системы:
приложение не вводит собственную нормализацию регистра.

### 10.2. Источники и назначения

Все выбранные источники должны находиться в одной родительской папке.
При UI-выборе это гарантировано ограничением на один уровень; сервер
не полагается на UI и отклоняет запрос с источниками из разных папок (400).

Запрещены:

- источник и назначение, обозначающие один объект;
- копирование/перемещение в ту же родительскую папку;
- перенос каталога внутрь самого себя;
- перенос каталога в собственного потомка;
- исходный список, одновременно содержащий каталог и его потомка;
- изменение корня;
- операция с неподдерживаемым объектом.

Целевой папкой может быть любой разрешённый каталог, включая каталог
другого корня. Запрещено выбирать в качестве цели:

- текущую папку;
- выбранный исходный каталог;
- потомка выбранного исходного каталога.

Родительская папка выбранного файла допустима как целевая.

Копирование и перемещение между любыми корнями разрешены.

Точные дубликаты выбранных источников удаляются до исполнения.

Порядок обработки источников: сервер сортирует их по полному
публичному пути с ordinal-сравнением строк. Порядок выбора в UI
не учитывается.

### 10.3. Изменение данных сторонними процессами

Снимок файловой системы не создаётся.

Если источник изменился или исчез, операция может завершиться ошибкой.
Приложение не обещает консистентную резервную копию активно изменяемых данных.

### 10.4. Частичный результат

Операции над несколькими объектами не являются общей транзакцией.

При ошибке:

- уже завершённые объекты не откатываются;
- существующие чужие данные не изменяются;
- результат содержит выполненные и неудачные элементы;
- пользователь явно видит частичное выполнение.

### 10.5. Двухфазная модель copy/move/delete

Операции над несколькими объектами не являются общей транзакцией.

Для `delete` целевой каталог и конфликты имён не проверяются; вместо
них действуют ограничения §9.5 (read-only, служебные файлы, временные
артефакты, symlink).

1. **Предварительная проверка** (этап `scanning`):
   - проверяются источники, целевой каталог, конфликты имён, symlink,
     неподдерживаемые объекты и вложенность;
   - собираются **все** найденные ошибки;
   - при наличии хоть одной ошибки операция не начинается;
   - задача получает `failed` и показывает сгруппированный список ошибок
     по объектам.

2. **Выполнение**: идёт по отсортированному списку источников
   и останавливается на первой фактической ошибке:
   - текущий объект получает ошибку;
   - последующие верхнеуровневые объекты помечаются как необработанные;
   - уже завершённые объекты сохраняются;
   - задача получает `failed` с указанием ошибочного объекта.

Порядок обработки не зависит от конкурентных задач; конфликты
определяются фактическим порядком публикации (см. 10.1).

Удаление выполняется только для одного объекта за раз.

### 10.6. Поиск

Поиск выполняется синхронно в рамках HTTP-запроса чтения; фоновая
задача и поисковый индекс не используются.

- область поиска — один корень (обязательный параметр) плюс
  опциональный стартовый каталог; обход рекурсивный вглубь;
- обход выполняется через общий валидированный walker: символические
  ссылки не просматриваются, неподдерживаемые объекты исключаются,
  служебные `.filebrowser-*` скрыты;
- сопоставление имени — подстрока без учёта регистра
  (ordinal-ignore-case); регистронезависимость является свойством
  сопоставления запроса, а не семантики файловой системы (§10.1);
- опциональный фильтр `ext` — glob-шаблоны (`*`, `?`, `[...]`),
  перечисляемые через запятую; шаблон сопоставляется с полным именем
  объекта, также без учёта регистра; невалидный шаблон отклоняется;
- обход ограничен лимитом результатов (не более 500, по умолчанию
  500) и бюджетом времени (60 с); досрочная остановка по любому из
  ограничений — штатный режим с флагом `truncated: true` в ответе,
  а не ошибка; это осознанное расхождение с двухфазной моделью
  §10.5, где частичное выполнение является ошибкой: частичный
  список совпадений полезен, задача copy/move — нет;
- сортировка результатов совпадает с сортировкой списка каталога
  (§9.2): каталоги, файлы, неподдерживаемые, внутри групп — ordinal
  по имени; собственной сортировки по релевантности нет;
- отмена: обход получает токен отмены от HTTP-запроса
  (`RequestAborted`);
- поиск с `root=AllRoots` (виртуальный корень, §7.1) выполняется
  по всем доступным реальным корням: обход каждого корня от его
  корня; недоступные корни пропускаются и перечисляются
  в `unavailableRoots` ответа; лимит результатов и бюджет времени
  — общие на весь запрос; пути результатов начинаются с имени
  реального корня, что делает их самодостаточными для отображения.

## 11. Загрузка файлов — не входит в MVP

Загрузка файлов на сервер в MVP не реализуется. Направление отложено
в `docs/ROADMAP.md` и проектируется отдельно перед началом работы;
решения, обсуждавшиеся ранее, обязательными не считаются.

## 12. Download

### 12.1. Один файл

- обычный HTTP stream;
- корректный Content-Disposition;
- application/octet-stream;
- без открытия пользовательского HTML/SVG inline;
- Content-Length, если известен;
- поддержка Range через стандартные возможности ASP.NET Core.

### 12.2. Папка и набор объектов (ZIP)

Скачивается папка рекурсивно либо набор объектов одной родительской
папки (§10.2). Скачивание `AllRoots` целиком (все корни сразу) запрещено;
скачивание реального корня разрешено. Путь под `AllRoots` делегируется
реальному корню так же, как при скачивании файла (§7.1): архив папки,
открытой через «Все корни», работает и получает обычные имя и структуру.
В самом списке корней допускается ровно один выбранный корень — он
скачивается как `<корень>.zip`; набор из нескольких корней сразу
отклоняется (`400 invalid_request`).

**Адресация.** `GET /api/fs/zip?ticket=…`. Тикет создаёт серверный
компонент UI после успешной предпроверки, поэтому ошибка подготовки
показывается в интерфейсе, а страница не заменяется JSON-документом.
Тикет — только адресация: он хранится в памяти, живёт 120 секунд,
допускает повторное использование в пределах TTL и теряется при
перезапуске. Тикет не является разрешением: корень, путь и тип каждого
объекта проверяются эндпоинтом заново через общий resolver/validator.

**Ответ.** `application/zip`, `Content-Disposition: attachment`
с UTF-8-именем: `<имя папки>.zip` — при скачивании одной папки берётся
её имя, при скачивании набора — имя текущей папки; для корня —
`<имя корня>.zip`.
`Content-Length`, `Accept-Ranges` и Range отсутствуют: архив
генерируется на лету и передаётся потоком. Заголовок `Cache-Control`
имеет значение `no-store`.

**Структура.** База архива — выбранная папка (если выбрана ровно одна
папка) либо текущая папка (если выбран набор объектов). Пути записей
считаются относительно базы, поэтому коллизии имён внутри архива
невозможны; при скачивании папки её содержимое лежит в корне архива,
без лишнего уровня. Пустые каталоги включаются явными записями
с завершающим `/`; архив пустой базы не содержит записей.
Служебные объекты `.filebrowser-*` исключаются и не обходятся.
Symlink и специальные объекты внутри дерева — отказ всего запроса
(`unsupported_object`); частичный архив не формируется.
Порядок записей — ordinal по полному имени записи.

**Сжатие.** Записи сохраняются без сжатия (`store`):
на типичном содержимом (медиа, архивы) deflate расходует CPU без
выигрыша в объёме.

**Двухфазность.** До отправки заголовков выполняется полная
предпроверка дерева без чтения данных: проверяются поддерживаемость
объектов, доступность, глубина, длина имён и лимиты. Любая ошибка →
ProblemDetails, тело ответа не начинается. Ошибка после начала ответа
(объект исчез, нет прав, отмена клиентом) обрывает соединение:
недокачанный архив не выдаётся за успешный, возобновление и докачка
не поддерживаются (§10.3). Для генерации на время запроса включается
синхронный ввод-вывод ответа — `ZipArchive` пишет синхронно; число
одновременных архивов ограничено (см. лимиты), поэтому блокировка
потоков ограничена.

**Лимиты (константы кода, не конфигурация).**

- записей в архиве — 50 000;
- суммарный объём (несжатый) — 200 ГиБ;
- глубина вложенности — 128;
- длина имени записи (UTF-8) — 1024 байта;
- одновременно формируемых архивов — 2, иначе `429 archive_busy`;
- бюджет предпроверки — 60 секунд, иначе `503 scan_timeout`.

**Коды ошибок.** `invalid_request`, `not_found`, `access_denied`,
`unsupported_object`, `root_unavailable`, `archive_too_large` (400),
`ticket_expired` (410), `archive_busy` (429), `scan_timeout` (503).

Скачивание архивом не является фоновой задачей: прогресса, истории,
отмены из панели задач и записи в SQLite нет.

## 13. Copy и move

### 13.1. Очередь

- BackgroundService;
- bounded Channel;
- ёмкость ожидающей очереди — 100;
- число workers из config.yaml;
- при заполнении — 429 с понятной ошибкой;
- SQLite хранит авторитетное состояние;
- Channel содержит идентификаторы задач, а не единственную копию данных.

Очерёдность выполнения — FIFO: задачи запускаются в порядке постановки
(`created_at`, при совпадении — `id`). Приоритетов нет; размер, тип
и источник задачи на порядок не влияют.

Сначала задача сохраняется, затем допускается к выполнению.
Ошибка помещения в очередь не должна оставлять вечную queued-задачу.

### 13.2. Состояния

- queued;
- scanning;
- running;
- cancelling;
- completed;
- failed;
- cancelled;
- interrupted.

`scanning` — предварительный обход и оценка объёма.
`cancelling` — получен запрос отмены, исполнитель останавливается.
`cancelled` — задача отменена пользователем (см. 13.8).

При старте queued/scanning/running/cancelling переводятся в interrupted.
Автоматическое продолжение и повторное исполнение отсутствуют.

### 13.3. Copy

Для каждого верхнеуровневого источника:

1. проверить источник и целевой каталог;
2. создать уникальный временный объект на стороне назначения;
3. скопировать содержимое;
4. закрыть файловые дескрипторы;
5. опубликовать под конечным именем без перезаписи.

Финальное имя появляется только после успешного копирования объекта.
При конфликте имени задача получает ошибку `name_conflict`; суффиксы
не подбираются (см. 10.1).

Preflight включает advisory-проверку свободного места: суммарный объём
источников сравнивается со свободным местом тома назначения, при
нехватке — ошибка `insufficient_space` до начала копирования.
Проверка не устраняет гонки (место может занять другой процесс или
задача): гарантией остаётся обработка ошибки записи в процессе
копирования. Если свободное место определить нельзя, проверка
пропускается.

### 13.4. Move

- сначала попробовать атомарное файловое переименование, если возможно;
- при переносе между файловыми системами использовать copy + delete;
- fallback разрешён при подтверждённой ошибке cross-device,
  а не при любом IOException;
- advisory-проверка свободного места (см. 13.3) выполняется только при
  переносе между томами: rename внутри тома места не требует;
- источник удаляется только после успешного копирования и публикации;
- секция «публикация → снятие регистрации временного объекта → удаление
  источника → фиксация объекта» не прерывается отменой: отмена, пришедшая
  после публикации, дожидается её завершения (см. 13.8);
- если удаление источника не удалось, задача failed;
- результат явно сообщает, что назначение создано, а источник мог сохраниться
  полностью или частично;
- автоматический откат назначения не выполняется.

Перед реализацией fallback необходимо подтвердить способ определения
cross-device ошибки для выбранной Linux/.NET-среды тестом.
Если переносимого managed API недостаточно, допускается небольшой
изолированный Linux-адаптер вместо эвристики по тексту исключения.

### 13.5. Временные объекты

Префикс: `.filebrowser-`.

Они:

- скрываются из обычного листинга;
- недоступны через публичные файловые операции: публичный путь с сегментом
  `.filebrowser-` отклоняется с `400/invalid_request`, включая чтение,
  переименование, удаление и copy/move;
- не создаются пользователем через API;
- регистрируются в SQLite до создания на диске.

После перезапуска приложение может удалять только точно зарегистрированные
собственные временные объекты, повторно проверив путь.

Удалять все файлы по маске `.filebrowser-*` запрещено.

### 13.6. Прогресс

- для каталогов предусмотрены этапы:
  - `scanning` — «Проверка и подсчёт»: процент не показывается;
  - `running` — копирование/перемещение: процент, обработанные байты,
    скорость относительно предварительной оценки;
  - `completed` / `failed` / `cancelled` / `interrupted`;
- во время scanning процент неизвестен;
- после сканирования известны оценочные bytes_total и items_total;
- bytes_done растёт по фактически скопированным байтам;
- скорость — скользящее окно 5 секунд;
- обновления UI — не чаще 2 раз в секунду на задачу;
- запись промежуточного прогресса в SQLite — не чаще раза в секунду;
  переходы состояния и финальный результат сохраняются сразу;
- после переподключения или потери уведомления состояние полностью
  перечитывается из SQLite;
- во время удаления источника move может оставаться на 100%,
  но не считается completed до завершения удаления;
- пустые деревья отображаются корректно без деления на ноль;
- при изменении источника оценка может перестать быть точной;
- переименование внутри файловой системы может завершиться сразу:
  задача считается completed после успешного атомарного rename,
  длительного прогресса и «искусственной» скорости нет.

### 13.7. История

Сохраняются:

- id;
- тип;
- список источников;
- назначение;
- состояние;
- текущий этап;
- bytes_done/bytes_total;
- items_done/items_total;
- стабильный код ошибки (`name_conflict`, `preflight_failed` и др.,
  см. `FileTaskErrorCodes`); исполнители задач работают вне HTTP-запроса,
  поэтому локализованные тексты в момент выполнения недоступны — перевод
  кодов выполняется при отображении; записи, созданные до введения кодов,
  содержат свободный текст и отображаются как есть;
- время создания, старта, обновления и завершения.

Результат хранится агрегированно по верхнеуровневым выбранным объектам:
для каждого — статус (обработан / ошибка / не обработан), для каталога —
счётчики обработанного и найденного, ошибочный путь и причина.
Детальные записи по каждому вложенному файлу не создаются.

Скорость допустимо хранить только в памяти.
При отсутствии активного выполнения отображается 0.

Панель показывает последние 50 задач с пагинацией; отдельной страницы
истории нет. Активные задачи всегда доступны.

Кнопка «Очистить историю» удаляет **все неактивные** задачи
(`completed`, `failed`, `cancelled`, `interrupted`) вместе с их результатом,
в рамках одной транзакции. Файлы при этом не изменяются. Удаляются только
задачи, неактивные на момент начала транзакции: если задача стала активной
одновременно с очисткой, она не удаляется.
Автоматического ограничения срока или количества записей нет.

### 13.8. Отмена

Отмена — пользовательское действие над активной задачей
(кнопка в панели задач; отдельного HTTP API нет).

Механика:

- у каждой выполняющейся задачи есть свой токен отмены (in-memory реестр);
  воркер связывает его с токеном останова приложения;
- кооперативная отмена: токен проверяется в цикле копирования (чанки),
  на границах объектов и во время предварительного обхода;
- отмена queued-задачи переводит её сразу в `cancelled`, воркер пропускает
  её при выборке из очереди;
- отмена scanning/running-задачи переводит её в `cancelling` и активирует
  токен; исполнитель останавливается на ближайшей точке проверки;
- отмена идемпотентна: завершённая, отменённая или несуществующая задача —
  отсутствие действия и ошибки;
- гонка отмены с завершением разрешается через guard переходов состояний:
  кто первым перевёл задачу, тот и зафиксировал результат;
- если отмена пришла после фактического завершения работы исполнителя,
  но до фиксации `completed`, задача переводится в `cancelled`,
  а выполненная работа сохраняется.

Результат отмены:

- текущий объект: временный артефакт удаляется, под финальным именем
  ничего не появляется, источник не изменяется; объект помечается
  `not_processed` с кодом `cancelled_by_user`;
- уже завершённые объекты сохраняются (частичный результат, отката нет —
  та же семантика, что при ошибке, см. 10.5);
- оставшиеся объекты помечаются `not_processed` с кодом `skipped_after_cancel`;
- задача получает `cancelled` с кодом `cancelled_by_user`;
- критическая секция move (публикация → удаление источника → фиксация,
  см. 13.4) отменой не прерывается;
- остановка приложения — не отмена: исполнитель не финализирует задачу,
  временный артефакт остаётся зарегистрированным для очистки при старте,
  задача при следующем запуске получает `interrupted` (см. 13.2, 13.5).

### 13.9. Delete

- тип задачи `delete`; поля назначения хранят исходную папку (общую
  родительскую папку источников) и информативны — схема БД не меняется;
- `scanning`: проверки §9.5, сбор всех ошибок, подсчёт узлов и объёма;
- `running`: для каждого объекта по порядку — регистрация временного
  артефакта в той же папке, переименование объекта в артефакт, удаление
  артефакта, снятие регистрации; затем объект `completed`;
- атомарная точка — переименование; участок «переименование → удаление
  артефакта → снятие регистрации» отменой не прерывается (как
  публикация → удаление источника в move, §13.4);
- прогресс и процент считаются по верхнеуровневым объектам; байты
  не используются, скорость не показывается;
- ошибка на объекте: объект `failed`, последующие `not_processed`
  (`skipped_after_error`), задача `failed` — двухфазная модель §10.5;
- отмена: текущий объект `not_processed` (`cancelled_by_user`),
  остальные `skipped_after_cancel`, задача `cancelled`;
- остановка приложения: задача остаётся активной, при следующем запуске
  переводится в `interrupted`, а зарегистрированный артефакт удаляется
  очисткой (§13.5);
- ошибка удаления артефакта после переименования — `delete_incomplete`:
  объект скрыт из пространства имён, место освобождается при следующем
  старте.

## 14. SQLite

- Microsoft.Data.Sqlite;
- параметризованные запросы;
- короткие транзакции;
- foreign keys включены;
- настроен busy timeout;
- изменения схемы через нумерованные миграции;
- выполненные миграции учитываются в БД;
- схема обновляется идемпотентно;
- соединения не разделяются небезопасно между потоками;
- одна операция файлового копирования не держит транзакцию БД открытой.

Минимальные сущности:

- schema_migrations;
- tasks;
- task_items;
- temporary_artifacts;
- app_settings (пары ключ/значение серверных настроек приложения;
  ключ `ui.language` хранит язык интерфейса `en` | `ru`).

Детальная SQL-схема определяется в итерации хранения,
но должна поддерживать контракты этого документа.

Миграция `1` создаёт:

- `schema_migrations(version, applied_at_utc)`;
- `tasks` с идентификатором, типом, статусом/этапом, публичным назначением,
  счётчиками, ошибкой и временными метками;
- `task_items` с публичным источником и агрегированным статусом элемента;
- `temporary_artifacts` с зарегистрированным публичным путём временного
  объекта.

Внешние ключи `task_items` и `temporary_artifacts` ссылаются на `tasks` и
удаляются каскадно. Миграция выполняется в короткой транзакции; соединение
настраивает `foreign_keys` и busy timeout 5 секунд.

Миграция `2` создаёт `app_settings(key TEXT PRIMARY KEY, value TEXT
NOT NULL)` — хранилище серверных настроек приложения, изменяемых через UI
(см. §9.6). Значение по умолчанию для языка — отсутствие строки
(`en`); сидирование не выполняется.

Для задач типа `delete` поля `destination_root`/`destination_path`
хранят исходную папку (общую родительскую папку источников); поле
информативное, схема не меняется.

Повреждённая или недоступная база останавливает запуск. Автоматическое
восстановление (`integrity_check`, переименование, пересоздание) не
выполняется: пользователь сам решает, как восстановить базу.

Автоматические резервные копии базы не создаются. README описывает
необходимость резервировать `/config` (app.db и config.yaml) средствами
владельца. Backup базы не должен выполняться поверх работающего приложения.

## 15. Обновления задач в Blazor

Отдельный TasksHub не создаётся.

- серверный сервис публикует уведомления об изменении задач;
- компонент подписывается на время жизни;
- обновляет UI через InvokeAsync;
- корректно отписывается;
- при новом подключении и переподключении полностью перечитывает
  актуальное состояние из SQLite;
- потерянное уведомление не приводит к потере задачи;
- можно выполнить ручное обновление списка.

Blazor-компоненты вызывают прикладные сервисы напрямую.
Не нужно заставлять серверный компонент вызывать собственное HTTP API.

HTTP-эндпоинты (скачивание файла и health-checks, §16) используют
те же прикладные сервисы, без дублирования правил.

## 16. HTTP-интерфейс

Внешний HTTP API удалён (решение «Удаление внешнего HTTP API»):
приложение — единственный полноценный клиент самого себя, и все
операции, кроме перечисленных ниже, выполняются через Blazor напрямую
в прикладных сервисах. Модифицирующих эндпоинтов нет; антиподделочные
токены antiforgery наружу не передаются и не требуются.

Общие правила для оставшихся эндпоинтов: DTO используют
root + относительный path; физические пути в ответах отсутствуют.

### Скачивание

- GET `/api/fs/download?root=...&path=...`
  - только один обычный файл;
  - поддерживается виртуальный корень (§7.1) — делегируется
    реальному корню;
  - поддержка Range;
  - корректный Content-Disposition (UTF-8 для не-ASCII имён);
  - `application/octet-stream`.

### Скачивание архивом

- GET `/api/fs/zip?ticket=...`
  - папка (рекурсивно) или набор объектов одной родительской папки;
  - выбор адресуется тикетом в памяти (SPEC §12.2), а не списком
    путей в URL: PATH-параметры с десятками элементов упирались бы
    в лимит длины строки запроса;
  - виртуальный корень `AllRoots` не поддерживается (`400`);
  - `application/zip`, `Content-Disposition: attachment`,
    `Transfer-Encoding: chunked`;
  - без `Content-Length` и без Range;
  - ошибка подготовки — ProblemDetails (§17); ошибка после начала
    ответа — обрыв соединения;
  - тикет не одноразовый: повторное скачивание в пределах TTL
    выполняется повторной генерацией архива.

### Предпросмотр

- GET `/api/fs/preview?root=...&path=...` — предпросмотр одного
  обычного файла для модального просмотрщика UI (§9.4);
- поддерживаемые типы определяются серверным whitelist расширений
  (`PreviewCatalog`), по содержимому файла тип не определяется:
  изображения (`png/jpg/jpeg/gif/webp/bmp/ico`), `pdf`, текстовые файлы
  (`txt/md/log/csv/json/xml/yml/yaml` и исходный код);
- поддерживается виртуальный корень (§7.1) — делегируется реальному
  корню;
- `Content-Disposition: inline` с корректным (в том числе не-ASCII)
  именем;
- изображения и PDF отдаются потоком целиком; PDF — с поддержкой Range
  (браузер запрашивает фрагменты для постраничного рендеринга);
- текст отдаётся не более чем первыми 512 КиБ (`text/plain;
  charset=utf-8`); при усечении выставляется заголовок
  `X-Preview-Truncated: true`; больший объём читается скачиванием;
- SVG и HTML в whitelist отсутствуют: их inline-отдача с того же origin
  привела бы к XSS (решение D084);
- видео и аудио не предпросматриваются и не планируются (§3, D085);
- файл с расширением вне whitelist → `415/preview_not_supported`;
- остальные ошибки и контракт ProblemDetails — общие (§17), тот же
  resolver/validator, что и для скачивания.

Health-checks — в §5.3.

Symlink и специальные объекты отклоняются. Ошибки эндпоинта
возвращаются как ProblemDetails с дополнительными стабильными
полями `code` и `traceId` (§17). Текст ошибки не содержит физический
путь.

## 17. Ошибки

Ошибки HTTP-эндпоинтов (скачивание и предпросмотр файла; health-checks
возвращают только статус) возвращаются как ASP.NET Core ProblemDetails:

- type;
- title;
- status;
- detail;
- code — стабильный машинный код;
- traceId.

`title` и `detail` локализуются по серверной настройке языка интерфейса
(§9.6); `code` и `traceId` не переводятся. Логи сервера остаются
на языке развёртывания и не переводятся.

Не раскрывать stack trace и физические пути.

Статусы:

- 400 — невалидный запрос или запрещённый публичный путь;
- 403 — нет прав ОС;
- 404 — объект не найден;
- 410 — тикет скачивания архивом неизвестен или истёк
  (`ticket_expired`);
- 415 — тип файла вне whitelist предпросмотра (`preview_not_supported`);
- 422 — неподдерживаемый тип объекта (`unsupported_object`);
- 429 — превышен лимит одновременных архивов (`archive_busy`);
- 500 — непредвиденная ошибка;
- 503 — корень недоступен или бюджет предпроверки архива исчерпан
  (`root_unavailable`, `scan_timeout`).

Для операции с частью ошибок внутри самой операции (например, задача
copy/move, остановленная на первой ошибке) применяется контракт задачи:
задача получает `failed`, результат содержит ошибочный объект
и необработанные объекты. Это не означает, что все объекты обработаны.

## 18. Наблюдаемость

Обязательно:

- структурированные console logs;
- traceId в ошибках;
- идентификатор задачи в логах задачи;
- логи старта, конфигурационных ошибок, задач и файловых ошибок;
- базовая ASP.NET Core tracing-инструментация;
- spans задач copy/move/delete и поиска;
- счётчик завершений поиска с флагом `truncated`;
- счётчик запросов скачивания архивом по результату
  (`completed`/`aborted`/`rejected`) и гистограмма несжатого объёма;
- метрики количества активных и ожидающих задач, завершений и ошибок;
- опциональный OTLP exporter через стандартные OTEL_* переменные.

Без настроенного exporter приложение продолжает работать.
Полный observability stack не является зависимостью основного Compose.

Все настройки экспорта — стандартные переменные `OTEL_*`
(например, `OTEL_EXPORTER_OTLP_ENDPOINT`). Документация содержит
инструкцию подключения приложения к внешнему OTel Collector, уже
развёрнутому отдельно, включая настройку endpoint, заголовков
авторизации и resource-атрибутов.

Содержимое файлов не логируется.
Пути файлов не используются как labels метрик.

## 19. Тестирование

### Unit

- правила имён;
- парсинг публичных путей;
- матчер подстроки и glob-шаблонов поиска;
- условия усечения результата поиска (лимит, бюджет времени);
- структура архива: имена относительно базовой папки, пустые
  каталоги, исключение `.filebrowser-*`, лимиты глубины и длины имени,
  отказ при symlink, запись без сжатия в не-seekable поток;
- конфликты имён;
- переходы состояний;
- расчёт скорости и прогресса;
- конфигурация.

### Интеграционные

С реальными временными каталогами и SQLite:

- границы корней;
- prefix confusion: `/data/a` против `/data/ab`;
- symlink в промежуточном компоненте;
- recursive operation с symlink;
- запрет изменения корней;
- copy/move между корнями;
- конфликт имён без перезаписи;
- временные объекты;
- частичное выполнение;
- восстановление статусов после рестарта;
- поиск: вложенные совпадения, исключение symlink
  и `.filebrowser-*`, усечение по лимиту, пустой результат,
  невалидный glob.

Через WebApplicationFactory:

- HTTP-контракт скачивания и Range;
- HTTP-контракт скачивания архивом: тикет (отсутствующий, неизвестный,
  истёкший), структура архива, отсутствие `Content-Length` и Range,
  ошибки до начала ответа, лимит одновременных архивов;
- ProblemDetails-ошибки скачивания: коды, traceId, отсутствие
  физических путей, локализация;
- health-checks (`/health/live`, `/health/ready`);
- рендеринг страниц UI (`/`, `/settings`);
- постановка задач, очистка истории, конфликты имён —
  через прямые вызовы сервисов и временные каталоги.

Не нужны моки для System.IO там, где проверяется реальное поведение ОС.

### Linux

Linux-тесты обязательны для проверки symlink и контейнерной среды.

Сценарий cross-device требует двух разных файловых систем.
Если тестовая среда этого не предоставляет, проверка явно отмечается
как невыполненная, а не как пройденная.

### Проверки

- dotnet build;
- dotnet test;
- docker build;
- docker compose config;
- запуск контейнера и smoke test.

Основные UI-сценарии проверяются вручную по чеклисту
(`docs/MANUAL_TEST_SCENARIOS.md`).

## 21. Правила итераций

Одна итерация — одна новая сессия модели.

В начале каждой сессии:

1. прочитать AGENTS.md;
2. прочитать docs/SPEC.md;
3. прочитать docs/PROJECT_STATE.md;
4. проверить git status и существующий код;
5. выполнить только выбранную итерацию.

Итерация не закрывается только потому, что написан код.
Необходимы проверки и обновлённый PROJECT_STATE.

Если предыдущий этап фактически не завершён, сначала сообщить об этом.
Не строить следующий слой поверх неработающего основания.

Коммиты создаёт пользователь, если отдельно не поручил это модели.

## 22. Критерии готовности MVP

Критерии ниже выполнены; раздел сохранён как зафиксированная граница MVP.

- все обязательные функции реализованы;
- приложение запускается в Linux Docker не от root;
- конфигурация валидируется;
- недоступный корень не останавливает запуск приложения;
- наружу не раскрываются физические пути;
- путь и symlink проверяются во всех операциях;
- нет перезаписи существующих данных; конфликт имени простой операции →
  409/name_conflict, а у задачи copy/move — ошибка задачи `name_conflict`;
- copy/move имеют определённую семантику частичных ошибок;
- download идёт обычным HTTP;
- задачи сохраняются, очередь FIFO, после рестарта помечаются interrupted;
- очистка истории удаляет только неактивные задачи;
- изменяющих HTTP-эндпоинтов нет (изменения — только через Blazor
  напрямую в сервисах), antiforgery остаётся внутренней инфраструктурой
  Blazor Web App;
- тесты проходят;
- выполнена Linux-проверка;
- выполнен контейнерный smoke test;
- ограничения описаны;
- PROJECT_STATE соответствует фактическому состоянию.
