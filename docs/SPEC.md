# Спецификация filebrowser

Требования к self-hosted веб-файлменеджеру. Известные расхождения реализации
и результаты проверок — в [PROJECT_STATE.md](PROJECT_STATE.md).
Нумерация разделов сохранена для ссылок из кода.

## 1. Назначение

Управление файлами через браузер для одного владельца или небольшой группы
в доверенной сети. Доступ ограничен каталогами, заданными в конфигурации.
Режим `ANONYMOUS` работает без входа; режим `LOCAL` включает локальные
учётные записи и cookie-сессии. Публикация в интернете не поддерживается.

## 2. Источники истины

Этот документ задаёт требования, код и тесты — фактическую реализацию.
Правила работы с репозиторием находятся в `AGENTS.md`, текущее состояние —
в `PROJECT_STATE.md`, эксплуатация — в `OPERATIONS.md`.

## 3. Границы продукта

Поддерживаются несколько корней, ленивое дерево, навигация через URL,
мультивыбор, поиск, создание папок, переименование, фоновые copy/move/delete,
отмена и история задач, скачивание файлов/ZIP, загрузка файлов,
предпросмотр изображений/PDF/текста, EN/RU и темы оформления.
Реализованы режимы `ANONYMOUS`/`LOCAL`, первичная настройка `admin`, вход,
выход, смена собственного пароля, локальное восстановление пароля `admin`,
управление пользователями через UI в `LOCAL`, хранение и серверная проверка
прав обычных учётных записей по корням, защита служебных каталогов и
привязка ZIP-тикета к создателю. Обычные учётные записи допускаются к
рабочему UI и файловым операциям в пределах выданных прав.

Не поддерживаются группы, саморегистрация, аудит-лог, внешние провайдеры
входа, квоты, редактор файлов, распаковка архивов, symlink и специальные
файлы, загрузка папок, докачка, продолжение/повтор задачи после перезапуска,
редактирование YAML через UI, управление ACL, сохранение всех метаданных,
кластерный запуск. Видео/аудиопредпросмотр, корзина и pause/resume не
планируются. Отдельный мобильный интерфейс не является целью. Направления
развития — только в `ROADMAP.md`.

## 4. Технологии

.NET 10 LTS, ASP.NET Core, Blazor Interactive Server, Minimal API,
Microsoft.Data.Sqlite (без EF Core), YamlDotNet, xUnit, OpenTelemetry.
Один серверный и один тестовый проект. Версии пакетов — в csproj, SDK —
в global.json. Без микросервисов, CQRS, mediator и отдельного SignalR Hub.

## 5. Развёртывание

### 5.1. Docker

Linux, multi-stage образ, порт 8080, непривилегированный процесс,
возможность задать UID/GID. Без privileged mode и Docker socket.
Compose по умолчанию публикует `127.0.0.1:8080:8080`; LAN-доступ требует
явного изменения binding и сетевых ограничений владельца.

### 5.2. Хранение

`/config/config.yaml` — конфигурация; `/config/app.db` — SQLite;
`/config` — постоянный writable volume, корни — отдельные mounts.
Один экземпляр приложения на БД. SQLite хранится на локальной ФС,
не на SMB/NFS. Резервное копирование — при остановленном приложении.
БД содержит историю, настройки, учётные записи и сессии; cookie также
зависят от ключей Data Protection, которые не входят в БД.

### 5.3. Health check

`GET /health/live` и `GET /health/ready` используют стандартные Health Checks.
Сейчас зарегистрированных проверок зависимостей нет: оба возвращают
`200 Healthy`, если приложение отвечает. Readiness **не проверяет SQLite**
или доступность корней. Проверки не записывают файлы и не раскрывают пути.

## 6. Конфигурация

```yaml
workers: 2
uploads:
  maxFileBytes: 8589934592
roots:
  - name: files
    path: /data
```

### 6.1. Правила

- Читается один раз при старте, hot reload отсутствует.
- `workers`: 1–16, по умолчанию 2.
- `uploads` необязателен; `maxFileBytes` — положительное целое число байтов,
  по умолчанию 8 ГиБ. Ограничивает файл и тело запроса загрузки.
- Нужен хотя бы один корень. `name`: `[a-z0-9][a-z0-9_-]{0,63}`,
  уникален без учёта регистра; это публичный идентификатор, его изменение
  ломает старые URL. `path` — абсолютный путь, в контейнере — путь внутри него.
- Корни не совпадают и не вложены друг в друга. Symlink в пути запрещён.
- Корнем может быть `/` или каталог со служебными файлами. Они видны;
  общей изоляции нет. Фоновое удаление защищает конфигурацию/БД (§9.5),
  но переименование и перемещение не дают такой гарантии.

### 6.2. Ошибки старта

Отсутствующий/невалидный YAML, неизвестные поля, невалидные значения,
дубликаты/пересечения корней, невозможность открыть/инициализировать SQLite
останавливают запуск. Повреждённая БД не пересоздаётся автоматически.

`ConfigPath` стандартной конфигурации ASP.NET Core по умолчанию равен
`/config/config.yaml`. `DatabasePath` по умолчанию — `app.db` рядом с активным
ConfigPath. Допускается размещение БД внутри корня с рисками §6.1.

### 6.3. Доступность корней

Отсутствующий каталог, отказ доступа, недоступная ФС, файл вместо каталога
или symlink делают корень недоступным, но не останавливают приложение.
Корень помечается в UI и проверяется заново при обращении/обновлении.
Клиент получает обобщённую причину, подробности допустимы в серверном логе.

### 6.4. Режим доступа

`AUTH_MODE` читается при старте. Отсутствие переменной означает `ANONYMOUS`;
допустимы `ANONYMOUS` и `LOCAL`. Пустое или неизвестное значение останавливает
запуск. YAML, сетевой binding и mounts от режима не зависят.

`ANONYMOUS` сохраняет доступ без входа ко всем настроенным корням, файловым
операциям, настройкам и общей истории. Управление учётками недоступно.
Сохранённые учётные записи и сессии не удаляются и не изменяются. Возврат в
`ANONYMOUS` означает, что анонимному посетителю снова доступны все корни и вся
история.

В `LOCAL` до появления `admin` первый посетитель задаёт пароль встроенной
учётке через форму первичной настройки. Пароля по умолчанию, приглашения и
саморегистрации нет. Создание выполняется атомарно: при конкурирующих
отправках сессию получает только победитель, проигравший переходит к обычному
входу. Наличие старых задач и настроек не мешает настройке. После создания
`admin` форма настройки закрыта. Логины уникальны без учёта регистра; `admin`
зарезервирован; внутренний ID неизменяем.

В `LOCAL` встроенная `admin` всегда существует после настройки, имеет полный
доступ ко всем корням и не удаляется, не переименовывается и не понижается.
Admin управляет обычными учётными записями на странице «Пользователи»:
создаёт учётку с временным паролем, выдаёт права по корням, сбрасывает пароль
и удаляет. Полномочия admin проверяются на сервере при каждом действии по
текущей сессии в SQLite. Логин — буквы/цифры Unicode, затем `.`, `_`, `-`,
1–64 символа. Временный пароль обязывает сменить его до доступа к UI, файлам
и задачам; при обязательной смене нельзя повторно задать тот же пароль
(ordinal-сравнение, без нормализации). Сброс и удаление отзывают прежние сессии; пароль `admin` меняется
им самим или локальной командой восстановления. Внутренний ID не используется
повторно: после удаления и повторного создания того же логина выдаётся новый
ID, а старые задачи сохраняют прежнего автора.

Пароли хранятся только как хеши штатного алгоритма ASP.NET Core Identity со
случайной солью. Пароли, хеши и идентификаторы сессий не попадают в логи и
DTO. Cookie аутентификации: `HttpOnly`, `SameSite=Lax`, `Secure` при HTTPS;
локальный HTTP поддерживается. Для HTTPS за доверенным прокси схема берётся
из forwarded-заголовков только для явно настроенных прокси. Ошибка входа
едина для неизвестного логина и неверного пароля; возврат после входа — только
на локальный URL.

### 6.5. Границы доступа

В `LOCAL` HTML-страницы приложения, файловые HTTP-маршруты и интерактивные
серверные действия требуют действующей учётной записи. Без сессии доступны
вход, первичная настройка до создания `admin`, публичные статические ресурсы и
health endpoints. При временном пароле разрешены только смена пароля, выход и
публичные ресурсы. После смены временного пароля обычная учётная запись
получает рабочий UI; файловые действия ограничены текущими правами по корням
(§8.5–8.6). Управление учётками — `/users` — доступно только `admin` и
недоступно в `ANONYMOUS`; проверка выполняется на сервере до рендеринга и
повторно в каждом административном действии. Ограничение по автору задач
действует для обычных учёток (§13.7).

Файловый HTTP без действующей сессии отвечает `401`, авторизованной учётке без
допуска или без прав на запрошенный корень/служебную ветку — `403`; ответы
имеют формат ProblemDetails и не заменяются HTML-редиректом. Отозванная/
истёкшая сессия и удалённая учётка перестают приниматься на следующем защищённом
запросе или серверном действии, включая уже открытый circuit: источник истины —
текущие строки SQLite. Выход прекращает доступ текущей сессии; визуальное
состояние вкладки обновляется при следующем действии или переподключении.
Смена/сброс пароля и удаление учётки отзывают прежние сессии, после собственной
смены выдаётся новая. Собственная смена пароля требует текущий пароль и
доступна обеим ролям.

Восстановление пароля `admin` выполняется локальной командой при остановленном
приложении, принимает пароль с консоли (не аргументом), меняет только `admin`
и отзывает его сессии. Команда работает с существующей БД.

## 7. Адресация файлов

Публичная ссылка: `{ "root": "files", "path": "folder/file.txt" }`.
Пустой path обозначает корень; разделитель — `/`. Запрещены абсолютные пути,
пустые внутренние сегменты, `.`/`..`, обратный слеш, NUL и некорректное
кодирование. URL декодируется HTTP-слоем один раз. Физические пути наружу
не передаются. Регистр существующих имён определяется файловой системой.

Новое имя — непустое одиночное имя, без `/`, `\`, NUL, `.`/`..` и префикса
`.filebrowser-`; не путь. Имена не приводятся к нижнему регистру.

### 7.1. Виртуальный корень

`AllRoots` объединяет реальные корни; это имя нельзя задать в YAML.
На верхнем уровне (`path` пуст) доступны листинг, поиск и скачивание одного
выбранного корня архивом; изменяющие операции запрещены (`400/invalid_request`).
Показываются только корни с правом чтения; недоступные по правам отсутствуют,
видимые, но недоступные на ФС — отображаются как недоступные элементы.

Путь `<имя корня>/<относительный путь>` делегируется реальному корню для
всех операций; права определяются по реальному корню. Сам реальный корень
допустим как назначение, но не как изменяемый/копируемый источник. Несколько
корней одним ZIP не скачиваются.

## 8. Безопасность файловой системы

Общий resolver проверяет root, синтаксис, нормализованный путь, границу
корня по сегментам и все существующие компоненты. Для нового объекта
проверяются родитель и имя. Проверки повторяются при исполнении задач.

### 8.1. Symlink и специальные файлы

Поддерживаются только обычные файлы и каталоги. В листинге подтверждённые
символические ссылки отмечаются отдельно, цель ссылки не показывается.
Выбор, переход, скачивание и изменение ссылки запрещены.
Рекурсивные операции не следуют по ссылкам; при предпроверке ссылка/FIFO/
socket/device означает отказ. Поиск пропускает неподдерживаемые объекты.

### 8.2. Ограничения защиты

Хост доверенный. Защита от враждебного локального процесса, заменяющего
компоненты между проверкой и открытием, не гарантируется. Строковая проверка
пути не является песочницей. Дополнительная граница — mounts и права ОС.
Не логировать содержимое файлов, не раскрывать физические пути и stack trace
в HTTP-ошибках. Ограниченная защита служебных файлов описана в §6.1 и §9.5.

### 8.3. Корни

Корень разрешено просматривать, искать, скачивать архивом, использовать
как назначение и создавать в нём объекты. Запрещено удалять, переименовывать,
перемещать и копировать корень как исходный объект.

### 8.4. Сеть

Permissive CORS запрещён. Изменения через GET запрещены. Единственный
изменяющий файловый HTTP-эндпоинт — POST upload с antiforgery; остальные
изменения выполняются Blazor через общие сервисы. Режим `ANONYMOUS` сохраняет
доступ без входа, режим `LOCAL` требует действующую учётку для страниц,
файловых маршрутов и интерактивных действий; публичные формы входа/настройки,
статические ресурсы и health endpoints доступны без сессии. Точные правила,
ответы 401/403 и ограничения admin-раздела заданы в §§6.4–6.5, 8.5–8.6, 9.8
и §16.
Таблицы пользователей создаются миграцией при старте и сохраняются при
переключении режима. Для GET скачивания и предпросмотра в `LOCAL` выставляется
`Cache-Control: no-store`, включая ответы с Range; в `ANONYMOUS` сохраняется
прежнее поведение.

### 8.5. Права на корни

Права обычной учётной записи хранятся в SQLite по имени настроенного корня:
`read` или `write`; отсутствие записи означает «нет доступа». Имя нового
корня прав автоматически не получает. Повторное использование имени корня
обозначает тот же корень для прав; оператор учитывает это при смене
физического пути. Внутренняя привязка — к неизменяемому ID учётной записи.

Матрица: `read` разрешает видеть корень, листинг, дерево и поиск, открывать
предпросмотр, скачивать файл и ZIP; `write` дополнительно разрешает создание
папки, переименование, upload/check, upload, удаление и использование корня
с любой стороны copy/move. `admin` и `ANONYMOUS` имеют полный доступ.

`AllRoots` показывает только доступные для чтения корни. Путь под
`AllRoots/<root>/...` сначала разрешается в реальный корень, затем применяются
его права. Прямая ссылка на недоступный корень даёт безопасный отказ; при
входе без явного root выбирается первый видимый корень. Если видимых корней
нет, показывается пустое состояние. Скрытые по правам корни не попадают в
`unavailableRoots` поиска; туда включаются только видимые, но недоступные
на файловой системе корни.

Политика едина для Blazor, файловых HTTP-маршрутов и точек исполнения задач:
проверки выполняются на каждом входе до выдачи метаданных или открытия файла.
UI отражает те же права: кнопки изменения, контекстное меню, drag-and-drop и
выбор назначения не предлагают действие без `write`. Актуальные права
перечитываются из SQLite на новом действии, поэтому ранее открытое дерево или
диалог не сохраняет устаревшие полномочия. Права выдаёт `admin` на странице
«Пользователи»; изменение действует для следующего запроса или действия.
Задачи дополнительно ограничены автором (§13.7); отзыв прав останавливает
исполнение на безопасной точке (§13.11).

### 8.6. Служебные каталоги в LOCAL

`ConfigPath` и `DatabasePath` допустимы внутри настроенного корня. Для каждого
активного файла внутри корня обычным учётным записям закрывается его
непосредственный родительский каталог целиком, включая содержимое и SQLite
sidecar. Если родитель совпадает с корнем, весь корень доступен только
`admin`. Если файлы разнесены по разным каталогам, закрываются оба; пути со
схожими префиксами не считаются одним каталогом. Сравнение выполняется по
нормализованным физическим путям и сегментам с учётом платформы. Если
служебный путь проходит через ссылки, учитываются заданные и фактические
родительские каталоги после разрешения каждого компонента и цепочек ссылок.
Физические пути клиенту не выдаются.

Для обычной учётной записи закрытый каталог и потомки отсутствуют в листинге,
дереве, поиске и выборе назначения; поиск пропускает ветку до обхода. Прямые
запросы и операции внутри каталога получают отказ, видимый предок остаётся
доступен для навигации и создания/загрузки объектов вне закрытой ветки.
Архив с рекурсивным выбором предка отклоняется целиком до HTTP-ответа;
copy/move/delete с таким предком в источниках проваливают предпроверку всей
пачки; переименование предка запрещено. `admin` сохраняет доступ в пределах
существующих ограничений на корни и операции со служебными файлами.

Защита не распространяется на копии БД, созданные администратором, и на
альтернативные пути к тем же данным через host aliases, mounts или hardlink:
конфигурация NAS считается доверенной.

## 9. Пользовательский интерфейс

### 9.1. Экран

Слева ленивое дерево с верхним узлом «Все корни», в центре таблица,
справа задачи. Перетаскиваемые разделители с минимальной шириной панелей.
Дерево и выбор назначения показывают только доступные корни и скрывают
служебные ветки. Над таблицей breadcrumbs, поиск и действия; в меню
приложения — настройки, а у `admin` в `LOCAL` — ещё и «Пользователи».

### 9.2. Таблица

Checkbox, имя, тип, размер, время изменения. Каталоги раньше файлов,
затем неподдерживаемые; внутри групп ordinal по имени. Размер каталога
не вычисляется (`—`); даты отображаются в часовом поясе браузера.
Длинные имена обрезаются визуально, полное имя — в tooltip.
Скрытые объекты видны, кроме `.filebrowser-*`. Мультивыбор — checkbox;
Ctrl/Shift-навигация не обязательна. Расширение имени не скрывается.

### 9.3. URL

`/?root=files&path=folder`; поддерживаются прямые ссылки и назад/вперёд.
Без root открывается первый видимый корень; недоступный по правам даёт
безопасный отказ. Ошибочный URL даёт ошибку с возможностью вернуться к корню.
Рабочая страница — `/`, `/browse` — 404.

### 9.4. Действия

Создать папку, загрузить, переименовать один объект, удалить один/несколько,
копировать/переместить с выбором назначения, скачать, предпросмотреть,
обновить. «Скачать» отдаёт один выбранный файл напрямую; папку или набор —
ZIP. Без выбора действие недоступно. В списке корней можно выбрать для ZIP
ровно один корень. Предпросмотр — двойной клик или контекстное меню.
Создание папки не зависит от выбора. Действия изменения доступны только при
`write` на текущий корень; выбор назначения показывает только корни с
`write`. Скрытые служебные ветки не появляются в списке, дереве и выборе
назначения. После операций UI обновляется; внешние изменения видны после
обновления/повторного открытия, watcher нет.

### 9.5. Удаление

Безвозвратное, рекурсивное, только фоновой задачей delete (§13.9).
Выбор — из одной текущей папки, не из поиска или списка корней.
Подтверждение: список объектов, предупреждение, checkbox, кнопка удаления.

Предпроверка запрещает корни, symlink/спецфайлы, недоступные объекты,
ReadOnly, деревья с активной конфигурацией, SQLite и её `-wal`/`-shm`,
с зарегистрированными временными артефактами. ReadOnly не снимается.
Для обычной учётной записи источник, являющийся служебным каталогом или его
предком, проваливает всю пачку; отдельный разрешённый сосед удаляется.
Назначения задач без зарегистрированных артефактов отдельно не защищаются.

Объект переименовывается в зарегистрированный артефакт той же папки,
затем удаляется. Имя освобождается при rename; ошибка удаления артефакта —
`delete_incomplete`, очистка повторяется при старте. Частичный результат
пачки не откатывается. Подробности отмены — §13.8–13.9.

### 9.6. Состояния и настройки

UI показывает загрузку, пустую папку, недоступность, исчезновение объекта,
ошибку операции, потерю связи, недоступное действие и неопределённый прогресс.

`/settings`: тема (системная/светлая/тёмная, localStorage, сразу), язык
(en по умолчанию/ru, SQLite `ui.language`, общий для клиентов, применяется
после полной перезагрузки). Неподдерживаемый язык отклоняется до записи.
В `LOCAL` глобальный язык меняет только `admin`; остальные учётные записи
видят действующий язык и могут менять тему. В `ANONYMOUS` язык доступен
без входа. Кнопка «✕» всегда возвращает на `/`. Серверная конфигурация
меняется в YAML и применяется после перезапуска.

### 9.8. Пользователи

`/users` доступна только встроенной `admin` в `LOCAL`; прямой адрес для
обычной учётки и в `ANONYMOUS` перенаправляется в `/access-denied` или `/`.
Страница показывает логин, роль, состояние (активна/временный пароль) и права
по корням. Admin создаёт обычную учётку с временным паролем и правами
`нет доступа`/`чтение`/`чтение и запись` для каждого настроенного корня,
редактирует права, сбрасывает пароль и удаляет учётку с подтверждением.
Сохранение формы заменяет права для всех текущих корней: пропущенное поле и
`нет доступа` снимают право. Записи для временно отсутствующих в YAML корней
сохраняются и восстанавливаются при возвращении того же имени.
Встроенная `admin` защищена от удаления, сброса и изменения прав. Дубликат
логина и зарезервированный `admin` отклоняются. Все действия проверяют
полномочия на сервере по текущей сессии SQLite. Интерфейс EN/RU.

### 9.7. Поиск

Query `q` переключает таблицу в результаты; `highlight` подсвечивает файл
после перехода в его родительскую папку. Клик по каталогу открывает его.
Под именем результата — родительский путь с корнем, полный путь — tooltip.
Checkbox и файловые операции в результатах не предоставляются.
Скрытые служебные ветки не попадают в результаты. Пока поиск идёт, показан
индикатор; обход не блокирует UI-контекст. Все подписи локализованы EN/RU.

## 10. Политика файловых операций

### 10.1. Конфликты имён

Существующее имя — ошибка `name_conflict` (HTTP 409 там, где есть HTTP).
Без перезаписи, объединения каталогов и автосуффиксов. Одна проверка Exists
недостаточна: публикация обязана исключать конкурентную перезапись.
Конкурентные задачи не резервируют конечное имя: выигрывает первая публикация.

### 10.2. Источники и назначения

Источники из одной родительской папки; точные дубликаты удаляются,
порядок — ordinal по полному публичному пути. Запрещены источник=назначение,
назначение в исходной родительской папке, перенос/копирование каталога
в себя/потомка, список с каталогом и его потомком, корень как источник.
Назначение — любой доступный для записи каталог, включая другой корень.
Для copy/move обе стороны требуют `write`; UI и сервис проверяют ограничения
независимо.

### 10.3. Изменение данных сторонними процессами

Снимок ФС не создаётся. Изменение/исчезновение источника может вызвать
ошибку. Консистентная резервная копия активно меняющихся данных не обещается.

### 10.4. Частичный результат

Пачка не является транзакцией. Завершённые объекты сохраняются, чужие данные
не меняются; UI явно показывает выполненные, ошибочные и необработанные.

### 10.5. Двухфазная модель copy/move/delete

Сначала scanning: проверки всех верхнеуровневых источников, назначения,
конфликтов, вложенности и дерева; собираются все найденные ошибки. Любая
ошибка останавливает всю пачку до исполнения (`failed/preflight_failed`).
Для delete вместо назначения/конфликтов действуют ограничения §9.5.
При обнаружении символической ссылки внутри источника результат показывает
её публичный путь относительно корня, без физического пути и цели ссылки.

Исполнение идёт по порядку до первой фактической ошибки. Текущий объект
получает ошибку, последующие — not_processed, задача — failed. Уже
выполненное сохраняется. Объекты пачки обрабатываются последовательно.

### 10.6. Поиск

Blazor вызывает сервис напрямую, отдельного HTTP API/индекса/фоновой задачи
нет. Рекурсивная область — root и необязательная стартовая папка.
Имя сопоставляется по подстроке ordinal-ignore-case; сервис также принимает
`ext` (glob `*`, `?`, `[...]`, через запятую), невалидные glob отклоняются.
UI предоставляет поиск по подстроке, отдельного поля ext нет.

Общий walker пропускает ссылки/спецфайлы/исчезнувшие узлы и `.filebrowser-*`.
Лимит — до 500 результатов (по умолчанию 500), бюджет — 60 с; достижение
лимита/бюджета возвращает частичный результат с `truncated: true`.
Сортировка как у листинга. Токен отмены передаёт вызывающий компонент.
AllRoots использует общий лимит/бюджет, пропускает корни без права чтения
и закрытые служебные ветки, возвращает в `unavailableRoots` только видимые,
но недоступные на ФС корни; пути результатов включают имя корня.

## 11. Загрузка файлов

### 11.1. Передача байтов

Один файл — один `POST /api/fs/upload` с raw `application/octet-stream`,
Content-Length и antiforgery `X-CSRF-TOKEN` из формы страницы. Браузер
передаёт файл напрямую, circuit получает только метаданные/события.
Несколько файлов выбираются кнопкой или drag-and-drop в текущую папку.
Назначение (root/path) фиксируется при выборе файла: навигация влияет
только на новые элементы очереди. В поиске и на верхнем уровне AllRoots
загрузка запрещена.

Необязательный query-параметр `uploadId` (GUID) связывает элемент
браузерной очереди с задачей до её создания. Повторное использование
существующего/чужого идентификатора отклоняется; отмена из UI идёт через
Blazor-сервис задач и не подменяется XHR abort.

### 11.2. Предварительная проверка

До тела проверяются root, права `write`, родитель, имя, отсутствие конечного
объекта, закрытая служебная ветка, лимит и свободное место (advisory).
Ошибка не создаёт задачу. GET upload/check выполняет те же проверки, но не
резервирует имя.

### 11.3. Временный объект и публикация

До создания на диске регистрируется `.filebrowser-<taskId>-<guid>`.
Байты пишутся туда; после полного приёма — публикация без перезаписи.
Частичного файла под конечным именем не бывает. Проигравшая конфликт
загрузка удаляет свой временный файл, существующий объект не меняется.

### 11.4. Ошибки, обрыв и отмена

Ошибка записи/конфликт → cleanup и failed с кодом. Обрыв/закрытие вкладки →
cleanup и `failed/upload_aborted`. Пользовательская отмена из окна загрузки
или панели задач → cleanup и `cancelled/cancelled_by_user`; ответ POST —
409 `upload_cancelled`. При незавершённой передаче браузер может не получить
ранний ответ и сообщить обрыв соединения. Окно загрузки сверяет итог с SQLite
через Blazor по `uploadId`; без подтверждённого итога показывает ошибку сети.
Отмена до создания задачи не создаёт задачу.
Если cleanup невозможен, регистрация сохраняется для следующего старта.
Остановка приложения оставляет активную задачу и регистрацию; при старте
задача становится interrupted, артефакт очищается. Если отмена принята
после публикации файла, но до completed, файл и успешный элемент
сохраняются, задача становится cancelled; после completed отмена — no-op.
Общая гонка отмены с завершением описана в §13.8.

### 11.5. Лимиты

Файл и тело запроса ограничены `uploads.maxFileBytes`. UI отправляет не более
двух файлов одновременно; серверного лимита числа загрузок и квот нет.

### 11.6. Представление в задачах

Одна upload-задача на файл, прогресс/скорость/отмена и история (§13.10).

## 12. Download

### 12.1. Один файл

Обычный HTTP stream, attachment с UTF-8 именем, application/octet-stream,
Content-Length, если известен, Range. HTML/SVG не открываются inline.

### 12.2. Папка и набор объектов (ZIP)

Потоковый ZIP без промежуточного файла, записи NoCompression (store).
Папка: содержимое в корне архива, имя `<папка>.zip`. Набор: пути относительно
текущей папки, её имя — имя архива. Для корня — `<корень>.zip`.
Пустые каталоги включаются, пустая база даёт пустой архив. Порядок записей
ordinal по полному имени. `.filebrowser-*` исключаются без обхода.
Спецфайл означает отказ всего запроса. Символические ссылки при предпроверке
считаются и пропускаются без следования; UI до скачивания требует явного
подтверждения «Скачать без ссылок» с количеством. Прямой выбор ссылки
отклоняется. Тикет сохраняет ordinal-упорядоченный набор относительных путей
ссылок; endpoint повторно сканирует дерево до ответа и отказывает, если набор
изменился, в том числе при замене ссылок при неизменном количестве. Поэтому
после подтверждения ссылки не могут быть пропущены незаметно. AllRoots целиком запрещён.

UI выполняет предпроверку и создаёт тикет в памяти на 120 с. В `LOCAL` тикет
привязан к ID создателя: чужой тикет ведёт себя как отсутствующий. Выдача и
погашение требуют актуального права чтения; эндпоинт повторно проверяет пути,
права и объекты до начала ответа. Тикет повторно используемый владельцем,
теряется при перезапуске и не является разрешением. Архив с рекурсивным
выбором закрытого служебного каталога или его предка отклоняется целиком.
Ошибка подготовки видна в UI без замены страницы JSON-ответом.

До начала ответа проверяются всё дерево, доступность и лимиты. Ошибка после
начала ответа обрывает соединение; обнаруженный после подтверждения новый или
изменённый набор ссылок отклоняется до начала ответа.
`application/zip`, attachment, `Cache-Control: no-store`, без Content-Length
и Range. На HTTP/1.1 используется chunked-передача. На время записи допускается
синхронный ввод-вывод ответа; число одновременных архивов ограничено.

Лимиты — константы: 50 000 записей, 200 ГиБ несжатых данных, глубина 128,
имя записи до 1024 байт UTF-8, 2 одновременных архива, предпроверка 60 с.
Превышение: `archive_too_large` (400), `archive_busy` (429), `scan_timeout`
(503). Нет задачи в SQLite, прогресса, отмены из панели и докачки.

## 13. Файловые задачи

### 13.1. Очередь

BackgroundService, bounded Channel на 100 ожидающих идентификаторов,
workers из YAML. SQLite — источник истины; задача сначала сохраняется,
затем допускается к выполнению. Переполнение даёт ошибку очереди и не
оставляет вечную queued-запись. FIFO (`created_at`, затем `id`), без
приоритетов. Upload исполняется HTTP-запросом, вне очереди.

### 13.2. Состояния

queued, scanning, running, cancelling, completed, failed, cancelled,
interrupted. Scanning — предпроверка, cancelling — запрос отмены.
При старте все queued/scanning/running/cancelling становятся interrupted,
автоматического продолжения нет.

### 13.3. Copy

Для объекта: повторная проверка → зарегистрированный временный объект
в назначении → копирование → закрытие дескрипторов → публикация без перезаписи.
Предпроверка сравнивает общий объём со свободным местом назначения.
Проверка advisory: невозможность опроса не блокирует работу; гонки за место
обрабатываются как ошибки записи. Права автора перечитываются в SQLite перед
каждым верхнеуровневым объектом и перед публикацией; отзыв до публикации
удаляет временный объект, оставляет конечное имя свободным, отмечает элемент
`not_processed/access_denied` и завершает задачу `failed/access_denied`.
Уже опубликованные объекты сохраняются.

### 13.4. Move

Сначала атомарный rename; fallback copy+delete только при подтверждённой
cross-device ошибке (Linux-проверка обязательна), не на произвольную IOException.
Проверка места нужна при межтомовом переносе. После копирования сначала
публикация, затем удаление источника; этот участок не прерывается отменой.
Ошибка удаления источника означает failed: назначение сохранено, источник
мог остаться полностью/частично; автоматического отката нет. Отзыв прав
проверяется перед объектом и перед публикацией fallback-копии; rename и
начатая публикация с удалением источника доводятся до конца.

### 13.5. Временные объекты

`.filebrowser-*` скрыты и запрещены в публичных путях, включая вложенные
сегменты. На Windows проверка префикса не учитывает регистр, на Linux
учитывает. Регистрация в SQLite предшествует созданию на диске. Очистка
при старте удаляет только точно зарегистрированные объекты с повторной
валидацией. Совпадение префикса без регистрации не даёт права удаления.

### 13.6. Прогресс

В scanning процент неизвестен. После сканирования bytes/items_total —
оценка; bytes_done — реально обработанные байты. Скорость — окно 5 с.
UI обновляется не чаще 2 раз/с на задачу, промежуточная запись в SQLite —
не чаще раза/с; переходы и финал сразу. Пустые деревья не дают деления на ноль.
В move 100% ещё не означает завершения удаления источника. Rename может
закончиться сразу, без искусственного прогресса. Вне исполнения скорость 0.

### 13.7. История

Сохраняются id, тип, публичные источники/назначение, состояние/этап,
счётчики, стабильный код ошибки и временные метки. Результаты агрегированы
по верхнеуровневым объектам, без записи на каждый вложенный файл.
Старый свободный текст ошибки отображается как есть, новые коды локализуются.

Каждая новая задача в `LOCAL` сохраняет неизменяемый ID запустившей её
учётной записи; ID берётся на сервере. В `ANONYMOUS` и у задач предыдущей
схемы автор `NULL`. Удаление учётной записи не меняет сохранённого автора и
не удаляет задачи, результаты и регистрацию артефактов. Повторное создание
того же логина даёт новый ID и не открывает старые задачи.

Панель показывает все активные задачи и историю страницами по 50. Обычная
учётная запись видит и отменяет только свои задачи, даже если позже лишилась
прав на корень; история сама по себе не даёт доступа к файлам. Admin видит
все задачи, включая старые и задачи удалённых учёток. Ограничение по автору
применяется к активным задачам, истории, пагинации, чтению по ID, отмене,
очистке истории, reconnect и сверке результата upload. Чужой ID ведёт себя
как отсутствующий и не меняет состояние задачи.

Очистка удаляет неактивные задачи всех четырёх типов и их результаты
в одной транзакции, не меняя файлы: обычная учётная запись — только свои,
admin и `ANONYMOUS` — все. Регистрация оставшихся артефактов должна
переживать удаление истории. Автоматического срока хранения нет.

### 13.8. Отмена

Queued → cancelled; scanning/running → cancelling и кооперативная остановка.
Повторная отмена, завершённая/несуществующая задача — без ошибки.
Отдельный токен останова приложения отличает shutdown от пользовательской отмены.

До публикации текущего объекта: cleanup временного объекта, источник цел,
элемент not_processed/cancelled_by_user. Завершённые объекты сохраняются,
остальные — skipped_after_cancel. Участок публикации и удаления источника
move не прерывается. Гонка завершения/отмены разрешается проверяемым переходом
состояния: если отмена принята до фиксации completed, результат сохраняется,
задача cancelled; после completed отмена ничего не меняет.

Отмена до создания строки задачи (upload по `uploadId`) связана с
инициатором. Заявка admin/системного доступа действует для любого автора,
заявка обычной учётки — только для её собственной загрузки. Чужая заявка
не отменяет чужую загрузку и не присваивает её ID; защита от дублирующего
`uploadId` сохраняется.

### 13.9. Delete

Destination хранит общую исходную папку. Scanning выполняет §9.5.
Running: регистрация → rename в артефакт → удаление → снятие регистрации →
completed элемента. После rename участок не прерывается отменой;
отмена и отзыв прав проверяются между объектами. Прогресс по
верхнеуровневым объектам, без скорости/байтов. Ошибки и частичность —
§9.5, §10.5, §13.8.

### 13.10. Upload

Создаётся сразу scanning, затем running; вне очереди. Источник элемента —
целевой публичный путь, destination — родитель; bytes_total = Content-Length,
items_total = 1. Скорость/прогресс как в §13.6. Завершение/ошибка/отмена — §11.4
и §13.8. Метрики очереди не применяются: у upload отдельные метрики.

Приостановленный приём тела периодически перепроверяет права автора в SQLite
и не ждёт следующего байта только ради проверки отзыва. Перед публикацией
права проверяются повторно; отзыв удаляет временный объект, оставляет
конечное имя свободным, отвечает `403/access_denied` и завершает задачу
`failed/access_denied`. Временные ошибки SQLite `BUSY`/`LOCKED` при проверке
повторяются на следующем тике; прочая ошибка проверки завершает запрос по
обычному пути ошибки загрузки, а обязательная проверка перед публикацией
сохраняется.

### 13.11. Отзыв прав автора

Worker перечитывает права автора задачи из SQLite перед стартом и на
безопасных точках: до следующего верхнеуровневого объекта и перед
необратимым действием над текущим, включая публикацию upload и rename
delete. Удаление учётки или потеря права записи на любой корень задачи
завершает ожидающую задачу `failed/access_denied` до изменений на ФС;
активная задача останавливается кооперативно. Завершённые объекты
сохраняются, остатки помечаются `not_processed/access_denied`, временные
объекты удаляются или остаются зарегистрированными для штатной очистки.
Начатая неделимая фаза move/delete доводится до согласованного конца.
Выход, смена и сброс пароля сами по себе права уже принятой задачи не
отзывают. Задачи без автора исполняются системным доступом; системные
операции очереди, прерывание при рестарте и очистка артефактов сохраняют
служебный доступ.

## 14. SQLite

Параметризованные запросы, короткие транзакции, foreign_keys, busy timeout
5 с, отдельное соединение на конкурентную операцию. Не держать транзакцию
при файловом вводе-выводе. Схема меняется нумерованными идемпотентными миграциями.

Сущности: schema_migrations, tasks, task_items, temporary_artifacts,
app_settings, users, sessions, user_root_permissions. Миграция 1 создаёт
хранение задач/артефактов; 2 — app_settings; 3 делает
`temporary_artifacts.task_id` nullable с `ON DELETE SET NULL`, чтобы
регистрация остатка переживала очистку истории; 4 создаёт `users` и `sessions`
(не более одной встроенной `admin` через частичный уникальный индекс; сессии
ссылаются на учётку и удаляются вместе с ней); 5 создаёт
`user_root_permissions` с правами `read|write` по имени корня и каскадным
удалением вместе с учёткой; 6 добавляет `tasks.author_user_id` (NULL для
анонимных и старых задач, без внешнего ключа: удаление учётки сохраняет ID).
Управление пользователями использует эти таблицы без новой миграции.
SQL-схема — в TaskDatabase. Язык хранится как
`ui.language=en|ru`, отсутствие строки означает en. Применённые миграции не
переписываются: изменение связи артефактов с историей выполняется новой
миграцией с сохранением существующих записей. Пароли хранятся только как хеши
со случайной солью; сессии содержат срок и признак отзыва.

При старте проверяется целостность БД. Недоступность/повреждение останавливает
запуск, автовосстановления и автобэкапов нет. Копия `/config` делается
средствами хоста при остановленном приложении.

## 15. Обновления задач в Blazor

Сервис уведомляет компоненты, подписка живёт столько же, сколько компонент,
обновление через InvokeAsync. При новом подключении/reconnect состояние
полностью перечитывается из SQLite; ручное обновление доступно.
Уведомление — не источник истины и не раскрывает чужие задачи: компонент
перечитывает активные задачи и историю с ограничением по автору (§13.7).
Отдельного TasksHub нет.

Blazor вызывает сервисы напрямую. Содержимое файлов (включая текст
предпросмотра) передаётся обычным HTTP, не через circuit. HTTP и Blazor
используют общие правила файловых операций.

## 16. HTTP-интерфейс

| Маршрут | Контракт |
| --- | --- |
| `GET /api/fs/download?root=...&path=...` | Один обычный файл, Range, attachment (§12.1) |
| `GET /api/fs/zip?ticket=...` | Потоковый ZIP (§12.2), неизвестный/истёкший тикет — 410 |
| `GET /api/fs/preview?root=...&path=...` | Один файл inline, правила ниже |
| `POST /api/fs/upload?root=...&path=...&name=...[&uploadId=...]` | Raw тело, Content-Length, X-CSRF-TOKEN; успех 201 и JSON `{root,path,size}` (§11). `uploadId` — необязательный GUID корреляции; невалидный — 400, занятый — 409 |
| `GET /api/fs/upload/check?root=...&path=...&name=...&size=...` | Read-only предпроверка, size необязателен; успех 204, не резервирует имя |
| `POST /auth/login`, `/auth/setup`, `/auth/logout`, `/auth/change-password` | Локальные формы входа, первичной настройки, выхода и смены пароля; antiforgery, cookie `filebrowser.auth` |
| `GET /health/live`, `GET /health/ready` | §5.3 |

Других файловых HTTP-операций нет. Параметры — публичные root/path, не
физические пути. Upload поддерживает пути под AllRoots, но не его верхний
уровень. Его ответы — no-store и nosniff. Неудача — ProblemDetails (§17).

В `LOCAL` все перечисленные файловые маршруты требуют действующей сессии:
без неё — `401/authentication_required`, учётке без допуска (временный пароль,
отозванная/удалённая запись) или без прав на запрошенный корень/служебную
ветку — `403/access_denied`. Прикладные сервисы применяют матрицу §8.5 и
защиту §8.6 к текущему актору. Ответы не подменяются HTML-редиректом. Формы
аутентификации принимают только POST с antiforgery; после входа допускается
возврат только на локальный URL. `ANONYMOUS` сохраняет файловые маршруты
без входа.

Предпросмотр: серверный whitelist PreviewCatalog по расширению, не содержимому.
Изображения png/jpg/jpeg/gif/webp/bmp/ico, PDF, текст/исходники.
Content-Disposition inline с UTF-8 именем; PDF поддерживает Range.
Текст — первые 512 КиБ, `text/plain; charset=utf-8`, при усечении
`X-Preview-Truncated: true`. SVG/HTML исключены для предотвращения исполнения
активного содержимого с origin приложения. Неподдерживаемый тип — 415.

## 17. Ошибки

HTTP-файловые ошибки — application/problem+json: type, title, status, detail,
code, traceId. Title/detail локализованы, code/traceId стабильны; без
физических путей и stack trace. Ошибка задачи хранится в результате задачи,
не выдаётся за успешную обработку всей пачки.

| HTTP | Коды |
| --- | --- |
| 400 | invalid_request, invalid_name, invalid_upload_id, antiforgery_failed, upload_incomplete, archive_too_large |
| 401 | authentication_required (LOCAL, файловый HTTP) |
| 403 | access_denied |
| 404 | not_found |
| 409 | name_conflict, upload_cancelled, upload_id_conflict |
| 410 | ticket_expired |
| 411 | length_required |
| 413 | file_too_large |
| 415 | preview_not_supported |
| 422 | unsupported_object |
| 429 | archive_busy |
| 500 | непредвиденная ошибка |
| 503 | root_unavailable, scan_timeout |
| 507 | insufficient_space |

## 18. Наблюдаемость

Структурированные JSON-логи в stdout, UTC, traceId; id задачи в её логах.
Логируются старт, ошибки конфигурации, задач и файловых операций; содержимое
файлов не логируется, пути не используются как labels метрик.

ASP.NET Core/runtime instrumentation, spans copy/move/delete и поиска;
метрики активных/ожидающих задач, завершений, ошибок, длительности, байтов
и объектов. Поиск учитывает truncated; ZIP — completed/aborted/rejected и
объём; upload — completed/failed/cancelled/aborted/rejected и объём.
OTLP опционален, стандартные OTEL_*; без exporter приложение работает.
Collector не является зависимостью Compose. Настройка — в OPERATIONS.

## 19. Тестирование

Unit для чистой логики; реальные временные каталоги и SQLite для файловых
сценариев/задач; WebApplicationFactory для HTTP. Проверяются границы корней,
symlink/спецфайлы, конкурентные конфликты, частичные ошибки, отмена/рестарт,
регистрация/очистка артефактов, сохранность истории и существующих данных,
лимиты, потоковый HTTP, antiforgery, локализация и безопасные ошибки.
Для авторизации проверяются режим по умолчанию и ошибка невалидного значения,
миграция существующей БД, конкурирующая первичная настройка, вход/выход,
antiforgery, 401/403 файловых маршрутов, смена/восстановление пароля и отказ
старой cookie. Для прав итерации 2 проверяются матрица no/read/write на
реальной ФС, прямой корень и AllRoots, чужой и устаревший ZIP-тикет, скрытые
служебные каталоги (оба пути, файл в корне, схожие префиксы, допустимый
сосед), отказ целой пачки и сохранность данных; HTTP-тесты охватывают
download, preview, ZIP, upload/check и upload. Для итерации 3 проверяются
миграция автора поверх предыдущей схемы, видимость задач двух пользователей и
старых строк без автора, отмена чужой задачи и pending-заявки, отказ worker
при отозванных правах и удалённой учётке, сохранение завершённого объекта,
очистка временного объекта при отзыве перед публикацией, отзыв во время
остановившегося тела upload. Для итерации 4 проверяются создание учётки с
временным паролем и правами, обязательная смена пароля, доступ обычной учётки
к UI и файловому HTTP по матрице прав, отказ прямому адресу `/users` и каждому
административному действию обычной учётки, запрет удаления/сброса/прав admin,
дубликат и зарезервированный логин, сброс и удаление с отзывом сессий,
сохранение авторства задач после удаления, ограничение глобального языка.
Linux-права, mount/cross-device
и специальные файлы проверяются в Linux. Интерактивный UI — по
MANUAL_TEST_SCENARIOS, не только статическим рендером.

Базовые команды: `dotnet build`, `dotnet test`,
`docker build -t filemanager .`, `docker compose config`.
Не выполненные проверки явно отмечаются в PROJECT_STATE.
