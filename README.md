# filebrowser

Self-hosted веб-файлменеджер для просмотра и управления файлами через браузер.
Рассчитан на одного владельца или небольшую группу пользователей в доверенной
домашней сети.

Требования и границы MVP — в `docs/SPEC.md`. Текущее состояние — в
`docs/PROJECT_STATE.md`.

## Статус (I10 — download)

Реализован каркас приложения: solution, Blazor Web App (Interactive Server),
HTTP-endpoint `/healthz`, тестовый проект, контейнерный запуск, строгая
загрузка YAML-конфигурации, безопасное разрешение файловых путей, чтение
корней/каталогов через Minimal API и Blazor UI для просмотра, создания папок,
переименования и удаления одного объекта, SQLite-хранилище и очередь фоновых
задач, фоновые исполнители copy и move, панель задач с серверными
уведомлениями, постановкой copy/move из UI и очисткой истории, а также
скачивание одного файла через `GET /api/fs/download` с Range.

## Конфигурация

Приложение читает YAML один раз при старте. По умолчанию требуется
`/config/config.yaml`; путь можно изменить стандартной настройкой ASP.NET Core
`ConfigPath`.

Перед локальным запуском создайте конфигурацию из примера и замените путь
корня на существующий абсолютный путь вашей ОС:

```powershell
Copy-Item config.example.yaml config.yaml
$env:ConfigPath = (Resolve-Path config.yaml)
dotnet run --project src/dotmeer.filebrowser
```

`config.yaml` не добавляется в Git. В конфигурации обязателен хотя бы один
корень, `workers` допускает значения от 1 до 16 (по умолчанию 2). Имена
корней уникальны без учёта регистра и соответствуют
`[a-z0-9][a-z0-9_-]{0,63}`. Корни не могут пересекаться между собой или с
каталогом конфигурации; символические ссылки в их существующих компонентах
запрещены. Имя корня является частью публичных ссылок, поэтому его смена
делает ранее сохранённые URL нерабочими.

Публичная адресация файлов использует только `{ root, path }`, где `path`
относителен и использует `/`. Абсолютные пути, `.`/`..`, обратный слеш и NUL
отклоняются. Физические пути не предназначены для клиентского контракта.

Недоступный корень не препятствует запуску: его доступность проверяется при
каждом обращении. Отсутствующий или невалидный `config.yaml` завершает запуск.

SQLite по умолчанию создаётся рядом с активным `config.yaml` как `app.db`
(обычный контейнерный путь — `/config/app.db`). Путь можно явно переопределить
стандартной настройкой ASP.NET Core `DatabasePath`, в том числе для тестового
хоста. Недоступная или повреждённая БД останавливает запуск; автоматическое
восстановление и резервные копии не выполняются. Резервируйте содержимое
`/config` средствами хоста только при остановленном приложении.

## Чтение файлов через HTTP API

- `GET /api/fs/roots` возвращает публичные имена корней и их текущую
  доступность;
- `GET /api/fs/list?root=files&path=documents` возвращает содержимое каталога.
  Параметр `path` можно опустить для корня;
- ответы содержат только публичные `root + path`, физические пути не
  раскрываются. Служебные `.filebrowser-*` скрыты из листинга, а прямой
  публичный путь с таким сегментом отклоняется `400/invalid_request`;
  неподдерживаемые элементы помечаются `unsupported`;
- ошибки возвращаются в формате ProblemDetails с полями `code` и `traceId`.

## Изменение файлов через HTTP API

- `POST /api/fs/mkdir` принимает `{ parent: { root, path }, name }`;
- `POST /api/fs/rename` принимает `{ source: { root, path }, newName }`;
- `POST /api/fs/delete` принимает `{ source: { root, path } }` и удаляет
  только один объект (каталог удаляется рекурсивно);
- все три запроса требуют antiforgery token из текущей страницы приложения и  связанный cookie. Токен передаётся в заголовке `X-CSRF-TOKEN`; отсутствующий
  или невалидный токен возвращает `400` и не изменяет файловую систему;
- конфликт имени возвращает `409` с `code: "name_conflict"`; существующие
  данные не перезаписываются. Корни, symlink и неподдерживаемые объекты
  изменять нельзя.

## Скачивание через HTTP API

- `GET /api/fs/download?root=files&path=documents/report.txt` отдаёт один
  обычный файл потоком: `application/octet-stream`, `Content-Disposition:
  attachment` с корректным именем файла (включая не-ASCII имена через
  `filename*=UTF-8''...`), `Content-Length`;
- поддерживается заголовок `Range` (`206 Partial Content`, `Content-Range`,
  `Accept-Ranges: bytes`);
- GET не требует antiforgery token;
- папки, корень, symlink, неподдерживаемые и служебные `.filebrowser-*`
  объекты не скачиваются: каталог и корень отклоняются `400/invalid_request`,
  отсутствующий объект — `404/not_found`, symlink — `422/unsupported_object`;
- физические пути не раскрываются, содержимое файлов в логи не пишется;
- скачивание папок и нескольких объектов (ZIP) в MVP не поддерживается.

## Задачи copy и move через HTTP API

- `POST /api/tasks/copy` и `POST /api/tasks/move` принимают
  `{ sources: [{ root, path }], destination: { root, path } }` и требуют
  antiforgery token в заголовке `X-CSRF-TOKEN`. Успешная постановка возвращает
  `202`, `{ "id": "..." }` и `Location: /api/tasks/{id}`;
- источники должны находиться в одной родительской папке; пустой список,
  корень в источниках и источники из разных папок отклоняются
  `400/invalid_request` до сохранения задачи;
- конфликт имени и ошибки предварительной проверки не возвращают HTTP `409`:
  задача переходит в `failed`, а причина и статусы верхнеуровневых объектов
  доступны в `GET /api/tasks/{id}`. Существующие данные не перезаписываются;
- copy создаёт временные объекты `.filebrowser-*` на стороне назначения,
  регистрирует их в SQLite до создания и публикует под конечным именем только
  после успешного копирования;
- move сначала выполняет rename в пределах одной файловой системы. При
  подтверждённой cross-device ошибке используется copy через зарегистрированный
  временный объект, публикация без перезаписи и только затем удаление источника.
  Fallback не применяется к произвольным ошибкам ввода-вывода;
- если после успешной публикации удалить источник не удалось, задача получает
  `failed` с явным указанием, что назначение создано, а источник мог
  сохраниться полностью или частично. Автоматический откат не выполняется;
- `GET /api/tasks?offset=0&limit=50` возвращает страницу задач; `limit` от 1
  до 50, сортировка — от новых к старым;
- `GET /api/tasks/{id}` возвращает одну задачу;
- `DELETE /api/tasks/history` удаляет все неактивные задачи (`completed`,
  `failed`, `interrupted`) вместе с результатом в одной транзакции, требует
  antiforgery token в заголовке `X-CSRF-TOKEN` и возвращает
  `{ "deletedCount": N }`. Активные задачи и файлы не изменяются;
- ответы содержат публичные `root + path`, состояние, этап, счётчики и
  безопасное описание ошибки, но не физические пути;
- `queued`, `scanning` и `running` задачи при старте приложения переводятся в
  `interrupted`. Очередь имеет ёмкость 100, число worker-потребителей берётся
  из YAML `workers`.

## Интерфейс

- `/browse` показывает дерево корней, таблицу каталога, breadcrumbs и панель
  задач;
- дерево загружает содержимое папки только при раскрытии соответствующего
  узла, не обходит всё дерево заранее;
- прямой адрес, например `/browse?root=files&path=documents`, можно открыть
  или сохранить. Навигация синхронизируется с историей браузера;
- выбор строк выполняется checkbox. Переименовать и удалить можно ровно один
  объект; при выборе нескольких объектов эти кнопки недоступны. Скачать можно
  ровно один выбранный файл: кнопка «Скачать» ведёт на
  `/api/fs/download?...`, при выборе папки или нескольких объектов она
  заблокирована; пункт «Скачать» есть и в контекстном меню файла. По правому
  клику строки доступно контекстное меню. Удаление требует явного
  подтверждения checkbox;
- «Копировать» и «Переместить» открывают окно выбора папки назначения с
  ленивым деревом. Текущая папка, исходные объекты и их потомки недоступны для
  выбора. Задача ставится в очередь через тот же прикладной сервис, что и
  HTTP API; конфликт имени выявляется задачей и не перезаписывает данные;
- панель задач всегда показывает активные задачи (`queued`, `scanning`,
  `running`) и историю неактивных задач страницами по 50. Для scanning и
  неизвестного прогресса показывается неопределённая полоса, для running —
  процент, байты, объекты и скорость из памяти. Ошибки и результаты по
  верхнеуровневым объектам показываются в карточке задачи;
- панель подписывается на серверные уведомления об изменении задач и
  отписывается при уходе со страницы. При подключении и переподключении
  состояние полностью перечитывается из SQLite; потерянное уведомление не
  теряет задачу. После завершения задачи файловый список обновляется;
- «Очистить историю» требует подтверждения и удаляет только неактивные задачи
  вместе с результатом; активные задачи и файлы не изменяются;
- `/settings` объясняет, что конфигурация меняется в `config.yaml`.

## Требования

- [.NET SDK 10](https://dotnet.microsoft.com/download/dotnet/10.0)
  (версия зафиксирована в `global.json`: `10.0.401`, политика roll-forward —
  `latestFeature`);
- Docker (опционально) для запуска в контейнере.

## Команды

### Сборка и тесты

```text
dotnet build
dotnet test
```

### Запуск локально

Профиль по умолчанию из `launchSettings.json`:

```text
dotnet run --project src/dotmeer.filebrowser
```

С явным адресом (внутренний порт контейнера — 8080):

```text
dotnet run --project src/dotmeer.filebrowser --urls http://127.0.0.1:8080
```

### Health check

`GET /healthz`:

```text
curl http://127.0.0.1:8080/healthz
```

PowerShell:

```powershell
(Invoke-WebRequest http://127.0.0.1:8080/healthz).StatusCode
```

Ответ работающего приложения: `200` с телом `{"status":"ok"}`.

### Docker

Сборка образа:

```text
docker build -t filemanager .
```

Запуск контейнера:

```text
docker run --rm -p 127.0.0.1:8080:8080 \
  -v ./config.yaml:/config/config.yaml:ro \
  -v ./data:/data filemanager
```

Compose (сборка + запуск):

```text
docker compose up --build
docker compose down
```

Перед первым запуском Compose создайте `config.yaml`:

```text
copy config.example.yaml config.yaml
docker compose up --build
```

## Контейнер

- Многоступенчатый `Dockerfile`: сборка в `sdk:10.0`, запуск в `aspnet:10.0`
  от непривилегированного пользователя (UID 1654 из образа; при необходимости
  переопределяется через `--user` / `user:` в compose);
- внутренний порт 8080 (`ASPNETCORE_URLS=http://+:8080`), только HTTP;
- `compose.yaml` публикует по умолчанию только loopback
  (`127.0.0.1:8080:8080`). Для доступа из LAN измените binding намеренно —
  сетевые ограничения в этом случае являются ответственностью оператора;
- `/config` — постоянный named volume для `app.db`; Compose монтирует
  `./config.yaml` в `/config/config.yaml` только для чтения. Сервис
  `config-permissions` перед запуском выдаёт named volume UID/GID процесса;
  по умолчанию это `1654:1654`, при необходимости задайте
  `FILEBROWSER_UID` и `FILEBROWSER_GID`;
- `./data` монтируется в `/data`, которому соответствует пример конфигурации;
- health check изнутри образа не настроен: в `aspnet`-образе нет `curl`.
  Проверяйте `GET /healthz` с хоста.
- Последняя Docker-проверка (2026-11-05, Linux engine через Docker Desktop):
  `docker build -t filemanager-i10 .` прошёл; образ запускается от UID `1654`;
  smoke-тест с временными config/data mounts вернул `200` на `/healthz`,
  полный download (`application/octet-stream`, `Content-Disposition`,
  `Content-Length`), `206` на Range-запрос (`Content-Range: bytes 0-4/33`),
  `400/invalid_request` на скачивание папки и подтвердил создание `app.db`.
- `docker compose config` подтверждён 2026-11-05. Изолированный
  `docker compose up` проверялся ранее, в I04: lifecycle запустил
  `config-permissions`, затем приложение; smoke-тест Compose вернул `200` на
  `/healthz` и `/browse`. Использовались отдельный временный project/volume и
  временные mounts, пользовательские данные не затрагивались.
- Образ .NET пишет ключи Data Protection в домашний каталог контейнера и
  предупреждает, что они не сохраняются при пересоздании контейнера и не
  зашифрованы. В текущем MVP нет авторизации или сохраняемого состояния сеанса;
  после пересоздания контейнера открытые браузерные сеансы могут потребовать
  обновления страницы.

## `/healthz`

- `200` — приложение готово обслуживать запросы;
- `503` — появится в следующих итерациях при введении критичных зависимостей
  (например недоступной SQLite);
- проверка не выполняет запись в корни данных;
- тело ответа не содержит физических путей.

## Известные ограничения

- Нет авторизации: приложение предназначено только для доверенной сети;
- загрузка файлов, скачивание папок и наборов объектов (ZIP), предпросмотр,
  поиск — вне MVP; скачивается только один обычный файл;
- cross-device move проверен на Linux tmpfs; на целевом NAS с реальными
  mounts рекомендуется повторить приёмочный сценарий;
- детальные правила — в `docs/SPEC.md` (границы MVP, §3).
